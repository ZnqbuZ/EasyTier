# HostRouteManager 第二步方案审查

审查对象：`docs/host-route-manager-step2-plan.md`（410 行，未提交）；代码及 master plan 基线：`de5afec6`。

**结论：暂不通过，修订后再开始实现。** 小型 Manager、原生/委托分支、成功后记账、不认领外部条目这些方向可以保留。主要问题是方案沿用了 step1 的概念示意，却没有落实最新 master plan 已明确的输入、创建记录和生命周期设计；部分示例还与验收目标直接矛盾。

这次不需要重写 master plan 或继续扩充 step1，也不需要添加通用框架。以下修改集中在固定来源读取、一个循环、绑定后端和宿主接线。

## R1 · P1：Core 计算函数依赖 Host 类型，按文件分工无法构建

**位置：方案第 45、99–121、159–167 行。**

`RouteSpec` 定义在 `easytier/src/instance/route/model.rs`，`UnmigratedRouteContext` 定义在 Host Manager 内，但 `easytier-core/src/peers/route/projection.rs` 的函数直接使用这两个类型。当前依赖方向是 `easytier → easytier-core`（`easytier/Cargo.toml:38`）；Core 不能反向引用 Host。这使 Batch 1 的“独立可构建”目标不成立。

**修改要求：** Core 保留 CIDR 规范化、manual 覆盖和只读业务事实；Host 在自己的计算函数内完成未迁移 writer 过滤、平台默认参数解析和 `RouteSpec` 生成。确需共享的纯业务类型可以定义在 Core，但不能为引用 Host 类型引入反向依赖。列清真实函数签名：现有 `resolve_proxy_cidrs` 接受拥有所有权的 peer 集合和配置快照，并非示例里的两个引用参数。

## R2 · P1：安装集合丢失创建身份，后端结果不足以支持可靠记账

**位置：方案第 49–50、103、123–139、228、233–234 行。**

方案只保存 `BTreeSet<RouteSpec>`，删除仍传 `RouteSpec` 或接口名字；没有 master plan 要求的创建记录。`ifname + ifindex + generation` 也没有进入每条记录与对应后端的绑定关系。接口名字被复用、后端换绑或默认参数改变后，无法证明删除的仍是创建时的条目。

`Result<(), Error>` 可以通过明确的类型约定表达部分结果，但本文没有这样的约定，反而要求所有失败下一轮重试。例如添加已产生副作用、接收确认失败，随后重试得到 AlreadyExists：该条目不会入账，停机也不会清理。删除精确目标已不存在的情况同样未定义，可能永久留在清理失败集合。

**修改要求：** 按 master plan 第 2.5 节，保存 `RouteSpec → InstalledRoute`，由绑定后端返回实际创建参数，删除接收该记录。明确 Created、AlreadyPresent、Removed、AlreadyAbsent、确定失败和结果不明的处理；结果不明先核实或报告阻塞，不套用普通失败重试。平台字段留在后端，不把 Linux table 扩散成通用 Host 路由身份；默认值先解析后比较。

后端实现任务还需明确：复用连接的请求/ACK 匹配、在目标 netns 中绑定连接和接口身份、阻塞调用的执行位置。目前 `netlink.rs:52–83` 是每请求建 socket 的同步收包逻辑，不能只保留旧实现再加一个“长期 socket”字段。具体记录与执行器只服务这个后端，无需抽象成框架。

## R3 · P1：动态过滤不能完成已安装条目的写入权交接

**位置：方案第 118–121、176–179、278–287 行。**

考虑文档承诺支持的变化：Manager 已安装 P，之后 Host 的 DNS/接口事实变化，使未迁移 writer 也需要 P。过滤器只让 P 从下一份 desired 消失，并不能让旧 writer 等待 Manager 完成删除。旧 writer 可能先收到 AlreadyExists 而启动失败，随后 Manager 又删除 P；若 Manager 删除失败，则冲突责任仍在。反向变化也必须等旧 writer 完成清理后才能释放排除范围。单纯“实时核对后抑制”无法保证第 287 行所说的任何时刻单一 writer。

此外，`UnmigratedRouteContext` 目前是静态字段值，没有更新入口；仅有 fake IP 不足以判断 DNS 是否启用、是否实际需要子网外 `/32`。这会使冲突范围与实际 writer 不一致。

**修改要求：** 选定具体交接方式。可以让冲突路由的写入职责同批进入 Manager；如果继续分阶段，则由现有 Host 生命周期顺序完成“预留冲突范围 → 等待原 writer 清理确认 → 启动接手 writer”，失败时不放行。DNS 启用、子网内外判断、DHCP 与接口准备事实必须进入该顺序。若某类变化只允许通过销毁旧 TUN 后重建实现，也应明确限制及销毁确认点。这里是具体生命周期顺序，不要求来源注册或通用事务协议。

验收补充：先安装代理 P、再让未迁移 writer 需要 P，以及反向交接；注入删除失败，确认后一个 writer 未被提前放行。只测试“初始输入已经重叠”不够。

## R4 · P2：输入接线缺失，所谓零分配与实际算法矛盾

**位置：方案第 105–113、172–188、198–208、230–231、298–316 行。**

方案宣称 `Route::list_proxy_cidrs()` 提供复用集合/借用迭代器，但现有公开方法返回拥有所有权的 `BTreeSet`，实际实现每次执行 `collect()`（`peer_ospf_route.rs:700–707`）。计算示例又每轮新建一棵 `BTreeSet`。等到 `installed == desired` 才跳过，前面的读取和分配已经发生，因此不能推导出“稳态零内存重分配”。每秒执行这条路径也违反 master plan 第 2.2–2.4 节。

另一方面，停用旧 monitor 通知后，本文没有写明谁更新 peer 快照、谁唤醒 Manager。Host 当前拿到的是 `CorePacketPlane`，内部 peer/config 字段私有；现有 `proxy_cidr_diff` 又受旧 monitor 可用性开关限制。声明 `Arc<dyn Route>` 和 `wake_tx` 不能代替实际接线。

**修改要求：** 增加一张小型输入表，列出每个来源的读取入口、快照提交点和通知入口。peer 集合在路由计算提交处缓存；配置复用 `CoreRuntimeConfigStore::snapshot()` / `subscribe_service_runtime_changes()`；Host 事实在实际 DHCP/TUN/DNS 提交处更新；新增 Core 读取入口独立于旧 monitor feature。先订阅后读初态，保证提交后通知及提交顺序。

循环缓存相关输入和 desired，相关事实未变时跳过计算，复用排序输出容量；保底核对改为低频，失败另设重试计时器。容量为 1 的 mpsc 本身不会自动合并所有发送：若使用它，需明确 `try_send` 满时忽略及关闭处理；直接复用 watch/Notify 更容易与拉取语义对应，不另建转发层。

## R5 · P2：调度会持续执行过时计划，失败项可被事件风暴反复重试

**位置：方案第 214–217、232–237 行。**

文档明确要求当前整轮完成后才处理新输入。若一轮有 10,000 条路由，在第 3 条执行期间需求撤销或接口失效，仍会继续执行余下旧操作；最后再收敛不能满足 master plan 已要求的变化响应和停止优先级。

失败项每次唤醒都重新出现在差集中，未设置逐项退避。不断到来的无关事件会让同一个失败被高频重发。“先全部 remove，再全部 add”还没有说明依赖同一系统槽位的替换：必要删除失败后，不能继续把添加视为独立操作。

**修改要求：** 完成在途操作并记账后，在下一项或有界批次边界检查停止、绑定和输入变化，丢弃未执行的旧计划。失败项保存有限的重试时刻，采用有上限退避，过时重试取消；独立项继续推进，相关替换遵守后端顺序。补充旧计划中途失效、事件风暴下重试上限及停止不饥饿测试，无需新增调度框架。

## R6 · P1：重绑定和 stop 只有成功路径，没有确定资源与清理责任的归属

**位置：方案第 52、238–249、380–386 行。**

接口重建仅描述“旧接口确认销毁后注销记录”，没有处理旧接口尚未确认销毁或清理失败时如何保存旧后端；单份 installed 加当前 binding 不能同时描述待清理旧绑定和新绑定。`generation + 1` 本身不能防止把旧记录交给新接口删除。

停机没有 master plan 中的 handle/deadline，也没有说明返回 CleanupIncomplete 后谁仍持有后端与在途工作。现有 `shutdown_runtime` 会取消任务并最终 `tun.shutdown()`；`TunNicState::install/stop/drain` 会替换或释放 NIC。只在 prepare/shutdown 两处加调用，覆盖不到 DHCP 建卡、静态 TUN 重建及资源释放顺序；DHCP 模式下 prepare 时甚至尚无可用网卡。

**修改要求：** 写出最小 `new/spawn/stop(deadline)` 入口与 Host 持有关系，明确 Manager 停止和 NIC 释放顺序。当前/待清理旧绑定各自保留对应安装记录和后端上下文，销毁确认或精确清理完成才释放；超时报告未完成并由原持有者继续跟踪在途操作。把 `runtime_host.rs`、`tun_desktop.rs`、`tun_common.rs` 及对应 DHCP/静态重建入口加入落点表。无需重构整个 NIC。

## R7 · P1：跨平台接管范围含混，委托端全量应用只有代理子集

**位置：方案第 11–13、144–147、214–217、259–266、388–410 行。**

唯一的 desired 计算只包含代理路由，委托分支却把它作为完整集合调用 `apply_routes`。移动宿主还有 DNS 等路由需求：例如现有 `mobile_vpn.ts:293–313` 会加入 Magic DNS `/32`。若按“完整期望集合”替换，会漏掉未迁移需求；若只是与旧代理计算结果合并，又破坏 manual 覆盖语义和单一写入者要求。applied 在会话失效后是否清空也没有定义。

实施批次实际只列 Linux 后端和原生宿主接线，平台矩阵只有 Linux、No-TUN 和模拟 Android，却以“全仓代理路由单一 Manager”作为完成门槛。定义 trait 和 Mock 不能证明 Windows/macOS/FreeBSD 或移动宿主完成接管。

**修改要求：** 明确每个平台在第二步的启用状态、真实后端/宿主文件、旧 writer 退出条件和验收范围。若某平台留到第三步，保留其旧生产链路并明确不声称已迁移；新接口不得使用默认空成功。若第二步启用委托后端，必须接到真实会话所有者，由它组装完整 VPN 配置、保留非代理需求、替换旧代理子集并取得应用确认；会话变化使旧 applied 失效，共享会话的实例不能分别重置同一个 VPN。只在这些实际平台边界上适配，不建通用跨实例框架。

## R8 · P2：示例 CIDR 构造没有清除主机位，反而会 panic

**位置：方案第 83–88 行。**

锁定依赖为 `cidr 0.3.2`。`Ipv4Cidr::new(addr, prefix)` 要求 addr 已经是网络地址，主机位非零返回 `InvalidHostPart`。输入 `10.0.0.1/24` 时，示例走到 `unwrap_or_else`，再次调用同一个必然失败的构造函数并 unwrap；根本不会进入 first_address 的 map。prefix > 32 也会 panic。

**修改要求：** 用 `Ipv4Inet::new(addr, prefix)?.network()` 或先校验前缀再清主机位，错误显式返回。已经是合法 `Ipv4Cidr` 的输入不需要重复规范化。保留主机位非零、/0、/32、非法前缀的针对性测试。

## 验收与事实表述校正

- 第 333 行“耗时下降 90% 以上”没有测量依据，不应先写成硬门槛。保留无逐条 dump、无重复建连等可验证要求，记录真实对比结果；单次请求也不意味着内核操作的整体复杂度必定 O(1)。
- 第 298 行暗示旧 monitor 稳态会反复系统写入不符合现有实现：`cidr_monitor.rs:165–192` 已检查变化且只发非空差异。性能对照应测真实旧实现，重点比较唤醒、计算/分配、失败收敛和后端操作成本。
- 按 master plan 第 7 节补齐 100/1,000/10,000 条、单条/批量变化、无关配置、通知竞态、部分失败与延迟分位数。Mock 测试能证明 Manager 决策，精确删除必须另有隔离环境中的真实后端测试；不能用 Mock 的相等比较证明内核删除匹配行为。
- 第 324 行 socket 次数按路由后端的单次绑定生命周期计量，允许重绑定/错误恢复重新建连；进程级 strace 还会包含其他业务，不能直接要求整个实例只有一次 socket 创建。
- 第 38、52 行应区分实际生命周期实现 `runtime_host.rs` 与转发 trait 实现 `runtime_host/implementation.rs`。旧 `route_demand` / `route_shadow` 当前并不存在，改为“不重新引入”，无需安排删除提交。

## 建议修订顺序

先修 R1/R4，确定 Core/Host 类型边界及真实输入接线；接着修 R2/R6，确定绑定后端、创建记录与生命周期；再把 R3/R5 的交接和调度顺序写进同一个循环，按 R7 列清平台范围。R8 直接改示例，最后同步五个实施批次与验收表。主体仍然是小型 Manager，不增加来源历史、版本令牌或通用状态框架。

本轮核对了方案全文、最新 master plan、step1 约定、现有 Core/Host/平台源码及本地 cidr 依赖源码。未修改方案正文或产品代码，未执行系统路由操作；此结论是实施方案审查，不是平台运行验收。
