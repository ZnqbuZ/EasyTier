# HostRouteManager 第二步方案：第九轮复审

审查对象：`0bd4407c`；[`host-route-manager-step2-plan.md`](host-route-manager-step2-plan.md) 内容哈希为 `cb4ffe640f930e2b82c1e033d9460f13c3d95967`。本文行号对应此版本（审查期间由工作区修订提交，内容未变）。

**结论：上一轮的命令丢失、future Send 约束、异步捕获提前释放均已修正；设备生命周期还剩两处接线问题。** 无需改动 Manager 主体架构，也无需恢复冻结协议。下一次修订应补具体 Host 资源和调用顺序，避免继续增加重复的“保证成立”描述。

## R1 / P1：选作保活对象的 VirtualNic 并不拥有 TUN，NicCtx 也不能等同于独立设备句柄

**位置：第 117–128、425–433 行。**

用真实资源的 Arc 替换 Notify、在 future 末尾显式 drop 的方向正确，但文中把 `Arc<VirtualNic>` 和 `Arc<NicCtx>` 当成可互换的底层设备保活方式，与现有源码不符：

- `virtual_nic.rs:243` 的 VirtualNic 只有 `global_ctx`、`ifname`、`ifcfg`，不持有设备文件描述符。持有它无法保活 TUN。
- `virtual_nic.rs:664` 将实际设备包装成 AsyncDevice，再由 BiLock 分给读写端；`NicCtx::run()` 第 1274 行将 tunnel 拆分后交给转发任务。
- NicCtx 持有的是这些任务的 JoinSet。延长 NicCtx 生命周期可以避免它被 Drop 时中止任务，但不能保证任务正常退出后，其 future 内的设备仍然存在。同时它会延长转发任务的生命周期；其中发送任务在第 910 行长期持有共享 packet receiver 的锁。因此“保活整个 NicCtx”和“仅保活设备供路由清理”有不同的关闭影响。

当前 `Arc<dyn Any + Send + Sync>` 只是擦除了这些差异，并没有补上资源关系。需要从真实设备创建处给出一条确定路径，不能继续把两种对象并列为等价实现。

**最小修正：** 明确 Host 如何取得并持有实际 TUN 资源，如何使该资源独立于转发 future 的退出持续到路由清理结束；可以调整设备持有结构，也可以选择明确的 Host 资源包和关闭顺序。删除 `Arc<VirtualNic>` 能直接保活设备的说法。若继续使用 NicCtx，则具体写出其设备持有改动及任务停止顺序，不能仅在外面套 Arc。一个具体资源类型足够，不要求新建通用保活抽象。

**验证：** 使用真实设备接线，先让转发任务退出，路由删除仍处于等待中；确认设备所需资源尚未释放，且后续关闭能释放旧 packet receiver，不阻碍 drain 或下一块设备接管。仅对模拟对象计数 Drop 不能证明这条 Host 接线正确。

## R2 / P1：只有“新设备已创建后的 Bind”，没有旧设备解绑到空状态的路径

**位置：第 252–261、303–313、361–369、428–433 行；完成通知顺序见第 489–496 行。**

当前换卡流程要求先构造新 TunDeviceHandle，再让 Manager 清理旧设备。这没有覆盖现有 Host 的先关闭再创建流程，尤其是没有新设备的情况：

1. `NativeDhcpIpv4Host::apply()`（`runtime_host/tun_desktop.rs:185`）首先 `self.nic.drain()`；当 `next == None` 时直接返回，不会再创建设备或发送 Bind。
2. 按本轮所有权方案，Manager 仍持有旧设备/上下文，而命令只有 Refresh、Bind 和永久 Stop，没有使 `current_tun_device` 变为 None 的设备生命周期入口。旧设备及路由可能继续存活；若持有整个 NicCtx，旧发送任务还可能继续占住 packet receiver，使 drain 无法接管。
3. 同名设备重建也需要先释放旧设备。若释放只能由携带“已创建的新设备”的 Bind 触发，创建与释放的前后关系就倒置了。换卡命令可靠入队解决不了这个问题。

**最小修正：** 定义一条 Host 可直接调用的解绑路径，表达 `旧设备 → 无设备 → 新设备`。例如将绑定操作扩展为接受 Option，并为解绑返回真实完成结果；也可复用已有关闭入口，只要不会连带永久停止仍要管理其他接口路由的 Manager。具体顺序是：

1. Host 请求解除旧默认 TUN；Manager 收束当前操作、处理该设备的记录，并释放自己的旧资源持有。
2. Host 完成相关转发任务退出和自身旧资源释放，确认可以继续创建；若没有新设备，保持无默认 TUN，其他接口路由继续由 Manager 管理。
3. 创建新设备后可靠绑定，重新读取输入并安装路由。

解绑失败或等待超时必须返回未完成并保留实际处理者，Host 不得据此宣称旧设备已释放。只需一次请求及一次完成结果，不引入 Frozen、多轮确认或通用交接框架。

`send().await` 的 Ok 只表示入队，不能当作上述解绑完成。同时当前清理代码先发 completion 再 `drop(device)`；若 Host 要据此开始同名重建，完成通知必须放在所承诺的资源释放之后，并考虑 R1 中真正持有设备的任务，而不能只等待一个 Arc 包装被丢弃。

**验证：** DHCP `Some(ip) → None` 后默认设备释放、Manager 不退出；再从 None 恢复或执行同名重建，旧设备先释放、新设备后接入；整个过程不丢弃其他接口的记录。增加解绑等待超时场景，确认 Host 不会误认为资源已经释放。

- `bind_tun_device` 使用 `send().await`，并在 Closed 时返还句柄：上一轮队列满静默丢命令的问题已关闭。这里不要求把所有刷新通知也改为可靠队列。
- RouteBackend 返回 future 显式声明 Send：上一轮泛型编译契约问题已关闭。
- 异步体末尾 `drop(device)`：上一轮捕获后提前释放的问题已关闭。
- master plan 容器说明和 step1 模型、接口已同步。
- 一个可顺手修正的编译问题：第 282 行 `DeviceBindError` 派生 Debug，但其字段 TunDeviceHandle 只派生 Clone。为句柄提供 Debug（输出设备身份即可），或改写错误的 Debug 实现。
