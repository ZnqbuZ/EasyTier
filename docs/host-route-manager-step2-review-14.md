# HostRouteManager 第二步方案：整体架构复审

审查对象：工作区 `host-route-manager-step2-plan.md`，内容哈希 `7a7ca7d7d53ae66b8a3c76d39056063c9eec51d7`。以下行号对应此版本。日期：2026-10-05。

**结论：职责方向已经改正，但当前方案仍不宜照着实现。应先把通知、协调和任务所有权各收成一条路径，同时修正下面的闭环缺口。无需继续增加框架或交接协议。**

用户提出的“device 和 refresh 共用一个 watch”应直接采纳，并扩展到所有刷新来源：**每个实例一个刷新 watch，所有来源提交事实后唤醒它；Manager 自己读取事实。** 设备信息不再作为独立刷新通道的载荷。

## 一、收敛后的架构

```text
Peer / 配置 / Host 接口状态 / DNS 状态
    ├─ 各自保存权威事实，Manager 通过现有入口读取
    └─ 提交事实后，通知同一个 watch<()>
                            ↓
一个 Manager 任务：读取 → 计算 → 增删 → 记账
                            ↓
编译期选定的平台后端：持有路由操作资源，不持有网卡

Host：独占网卡生命周期；持有 Manager 任务并等待清理结果
```

### 1. 一个刷新通道，不建立通知汇聚框架

- 删除 `device_tx/device_rx`、Manager 的 `peer_routes_rx/config_rx` 和公开刷新计数器。Manager 只收一个 `watch::Receiver<()>`。
- 装配时把同一个 `watch::Sender<()>` 的克隆接到实际提交点。先提交可读取的事实，再 `send_replace(())`。Core 接收标准库类型或 Tokio 类型，不依赖 Host 的路由模型。
- Core 现有供其他消费者使用的订阅可以保留；不要为接入 Manager 给每个来源再启动一个转发任务，也不要建立通用订阅注册中心。
- 设备状态留在 Host 的小型只读事实中；复用现有存储，缺失时才补一个。通知不携带设备事件历史，也不要求逐条收到 `Some → None → Some`。
- `watch<()>` 已足够表达“需要重新读取”。发送相同的 `()` 也能通知接收者，无需自己维护 `u64`。[Tokio Sender 文档](https://docs.rs/tokio/latest/tokio/sync/watch/struct.Sender.html#method.send_replace)

### 2. 一个协调入口，设备变化也是输入变化

删掉独立的异步 `handle_device_fact_changed → reconcile` 路径。设备处理可以是协调内部的短小同步辅助函数，不能形成第二个协调入口。

循环结构只需如下示意；这不是要求新增这些名字的公共类型或接口：

```text
先建立刷新接收端
循环：
    如已停止，退出循环
    在读取事实之前，标记当前刷新通知已读，并立即释放 watch 借用
    读取各来源最新事实；读取失败不能解释成空集合
    根据已确认的接口消失事实，结束对应记录的责任
    仅在相关输入改变时重算 desired
    执行必要且已到重试时间的增删，逐项记录结果
    在途操作完成后，如有新通知，重新读取；不继续长批次的过时计划
    等待：停止 / 同一个刷新 watch / 最近一次重试或低频核对时间
退出循环：
    再读取接口事实，处理已销毁接口
    清理仍需负责的路由，返回清理结果
```

第一次协调必须发生在第一次等待之前。处理期间到达的通知不能在处理结束时被顺手标成已读。watch 借用不能跨系统 I/O。[Tokio Receiver 文档](https://docs.rs/tokio/latest/tokio/sync/watch/struct.Receiver.html#method.borrow_and_update)

重试到期判断放在每轮协调内；合并保底核对与重试的最近截止时间即可，不需要多套定时调度组件。刷新风暴不能不断重置截止时间。

### 3. 一个任务所有者，一个完成结果

可克隆的只是刷新发送端。Host 独占停止控制与任务句柄，不要求整个 `RouteManagerHandle: Clone`。

- Manager 任务直接返回 `Result<(), CleanupIncomplete>`，正常停止时通过任务完成值取得结果。
- 删除两处共享 `cleanup_result`、共享 JoinHandle 锁，以及为了这两把锁增加的回退查询分支。
- 限时等待借用 `&mut JoinHandle`；超时保留句柄，Host 后续仍可等待。完成后消费句柄；只有真实调用方需要重复查询时，才在唯一所有者中保存一次终态。
- 等待超时表示任务尚未确认完成，不是已取得完整失败清单。不得拿空条目列表冒充最终清理报告。
- 如需在调用方退出时托管异步清理，可用项目选定的 guarden 等现成机制托管路由任务/后端；不得重新保活 TUN，也不再引入一个自制清理监督框架。

Tokio 明确区分丢弃 JoinHandle 与等待 `&mut JoinHandle`：前者使任务脱离句柄，后者可安全取消等待而保留结果。[Tokio JoinHandle 文档](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html#cancel-safety)

### 4. 保留必要状态，缩减模块

保留统一 `Route`、一个 `RouteError`、静态平台后端、`desired` 缓存、成功创建记录和必要的失败/未决记录。这些数据含义不同，不能为了行数把“期望存在”当成“本方已创建”。

主体建议按 `manager.rs`、`backend.rs`、必要时独立的 `policy.rs` 组织，短模型直接放模块入口；各平台实现单列。当前六个新文件并非错误，但没有必要预先强制 model、policy、backend 门面分别成文件。Mock 随测试组织。不要为每个来源抽一个 trait。

## 二、必须修正的闭环问题

### R1：停止等待会丢失任务句柄，且锁等待不受截止时间约束

位置：第 289–346 行。

`join_handle.lock().await` 在 timeout 外；第一个 stop 持锁等待任务，第二个 stop 可越过自己的 deadline。随后 `guard.take()` 把句柄移入 timeout，超时即丢弃句柄；第二次 stop 会看到 `None`，走“任务已完成”的分支，实际任务可能仍在运行。

**按上面的单一所有者设计删除共享锁路径，不继续增加 try_lock、结果锁和回退分支。** 区分等待超时、任务异常、清理完成但有失败；不要求因此新建一套通用 Outcome。

### R2：主循环漏掉首轮执行，部分退出绕过清理

位置：第 365–370、403–464、546–585 行。

文案说读取初态，但示例直接进入 select，没有执行初次协调；若初态已就绪且后续无更新，路由不会安装。任意 `changed()` 返回错误直接 `break`，又绕过只放在取消分支中的清理。

停止与设备销毁同时发生时，取消优先还会使清理沿用旧设备记录，把已随接口消失的未决路由报告为遗留。首轮主动协调、所有正常退出共用清理尾段、清理前重读接口事实，能一起解决。异常中止仍须如实报告，不能声称任何退出都保证清理成功。

第 393 行要求 30 秒保底核对，实际 select 没有对应时间来源；合并进一个下一次唤醒时间即可。

### R3：默认出口改变不能直接等同于旧接口已销毁

位置：第 148–157、515–533 行。

`old.ifindex != new.ifindex` 只能证明默认选择改变；如果旧接口仍活着，直接清空 installed 会遗留路由。必须明确 Host 当前路径是“确认旧设备销毁后才提交替换事实”，或者由平台查询确认；不得仅凭更换默认出口丢弃责任。外部指定接口同样不能套用默认 TUN 的销毁结论。

另外，“Linux ifindex 递增，因此是设备生命周期的确切身份”不能作为保证。Linux 允许创建接口时指定 ifindex，数值不是永不复用的实例标识。[rtnetlink 手册的 RTM_NEWLINK 说明](https://man7.org/linux/man-pages/man7/rtnetlink.7.html)

单 watch 会合并中间变化，最新事实必须足以区分重建。优先复用 Host 已有的设备实例身份；若没有，只补必要的本地实例标识，不建立版本框架，不持有设备资源。OS 接口索引负责系统调用定位，Host 实例身份负责识别自身设备重建，网络命名空间由后端上下文限定。不能据此声称解决了任意外部接口替换竞态。展示用 ifname 也不应单独导致路由删增。

### R4：AlreadyPresent 没有落在闭环状态中，会反复添加

位置：第 182–188、382–383 行。

`add → Ok(None)` 不入 installed 是正确的，但当前停止重复操作的条件只有 `desired == installed`。因此外部已存在条目始终留在差集中，每次刷新或保底核对又发一次 ADD。这与“稳态零写”矛盾。

必须明确其后续行为：用小型观察记录保存“已存在但非本方所有”，输入相关条件改变或明确重新核实时再处理，退出时绝不删除；不要把它塞进本方创建集合。该记录只随当前需求增长，不保存历史。EEXIST 若无法证明是等价路由，也不能直接标成已满足，应报告冲突并抑制重复尝试。

Unknown 的保守隔离可以保留，但这是“避免误操作并报告未决”，不是自动恢复。确认缺失可以结束相应未决；仅观察到路由存在不能反推它是本方创建。不要以最高可靠性为名重新扩展成所有权证明框架。

### R5：DNS 排除与交接已经没有完整定义

位置：第 45–55、354–363、599–645、701、743–746 行。

策略仍要求过滤未迁移 DNS 冲突，测试仍引用 Tracker 和释放预留范围，但输入表、事实维护和交接时序已没有相应定义。`DnsCleanOutcome` 只能描述清理，不能阻止 DNS 启动过程中和 Manager 双写。当前 DNS 构造函数仍直接添加路由，清理函数仍直接删除路由。

**架构建议：在本次 Linux 接管中一并迁移 DNS 的路由增删。** DNS 的 fake IP、是否需要接口外主机路由等事实参与同一次计算；同一有效路由由代理和 DNS 同时需要时合并，撤销一个来源不删除另一个来源仍需要的路由。DNS 服务、解析器和系统 DNS 配置仍由原组件负责。由此可以删除临时 Tracker、预留范围、路由写入权交接及路由专用 `DnsCleanOutcome` 传播链。

迁移需要明确 DNS 可用性顺序：不能在路由需求尚未成功处理时宣称 DNS 配置完成。沿用实际启停流程，只在确需确认的业务点等待具体结果；不要求所有刷新等待完成，也不借此引入通用版本等待 API。DNS 初始化失败须撤销其事实需求。上述顺序必须在实施接线中写清楚。

如果仍坚持本阶段保留 DNS 旧 writer，就必须补齐最小互斥和排除事实；仅修 clean_env 不够。综合最终架构和可删除的中间机制，优先选择同步迁移路由写入。

## 三、性能与范围调整

1. **持久连接与异步收包优先。** 第 217 行规定把阻塞 I/O 放入 spawn_blocking，只解决了阻塞调度器问题，不能直接视为性能最优。优先评估现有 Netlink socket 接入异步 readiness；必须阻塞时用受控执行环境并复用连接，避免每条路由一次线程池往返。连接绑定网络命名空间，通常无须随同命名空间内每次 TUN 重建而重建。
2. **一个底层实现。** 复用 `common/ifcfg/netlink_wire` 等现有编码设施。修改旧 ifcfg 与增加新 backend 时共用底层路由请求构造，避免维护两套精确删除实现。
3. **不要把吞吐上限定死在逐条往返。** Manager 保持一个逻辑写入者；先完成正确的串行版本，规模基准若表明 ACK 往返是瓶颈，再在后端对独立操作做有界批量、逐项记账。同槽替换维持必要顺序，不引入事务或每条路由一个任务。
4. **零分配、零写是验收指标，不是文字保证。** 首先避免无关配置重算、反复克隆 CIDR 集合和 AlreadyPresent 重试；BTreeSet 与排序 Vec 的选择由规模测试决定。业务保底核对不等于系统漂移检测，不能同时宣称持续修复外部路由修改。
5. **文档同步消除旧前提。** master plan 第 97、123、137–144 行仍保留多通知入口和每次 NIC 重建绑定/交接的表述，应同步为单 watch、Host 管设备、后端按网络作用域复用。第 171 行“当前树无 step2 文件”也已过时。step2 文件树中“cidr_monitor 移除向系统写路由逻辑”不准确：它发布事件，实际旧 writer 在 Host 的 updater。

## 四、下一次修订的最小交付

把方案压成：职责与输入、必要数据、单循环、平台操作、Host/DNS 接线、验证六部分。合并重复的规范、伪代码和验收清单；删掉共享结果锁示例和多 watch 循环，不在原文上继续叠补丁。

验证集中在能发现实际错误的场景：首启无后续事件；多个来源同时刷新；I/O 期间再次更新；设备销毁通知与停止同时到达；中间设备状态被合并；stop 超时后仍可等待；AlreadyPresent 重复刷新不重复写且退出不删除；DNS 与代理同路由的需求合并；部分失败和 Unknown；真实 netns 精确增删与规模性能。

本轮只新增审查文档，未修改方案正文或产品代码，未运行产品测试。静态架构审查可以确定上述删减方向，不能在实现及测量前证明“绝对最优”。
