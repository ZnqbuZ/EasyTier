# HostRouteManager 第二步方案：架构简化审查

审查基线：`ef552127`；方案为 [`host-route-manager-step2-plan.md`](host-route-manager-step2-plan.md)，Git blob `e80c62b26d6eecf936d302f0d67a3e9a61b514cd`。本轮依据用户对模型、错误、分发、清理、迁移范围和通知的六项反馈。

**结论：撤回上一轮“可直接按现方案实现”的结论，先做一次架构收缩。** 之前的审查逐项修补了行为漏洞，却没有充分审视解决方式的复杂度，导致方案积累了重复模型、运行时多态和多轮资源交接协议。用户要求的是小型 Manager，不能把这些机制作为可靠性的必然代价。

本轮意见替代此前对具体结构体、Outcome、动态后端、Frozen 和交接命令形状的要求。成功记账、精确删除、外部条目不认领、失败可见等行为要求继续有效。修订应删除或替换原章节，不能把本意见再附加成一层机制。

## A1：合并路由模型，接口是路由参数

**对应方案：第 3.1 节及后端接口。**

- 以一种完整 `Route` 表示生效参数；期望集合和成功创建集合均可使用它。不再手写 `RouteSpec` 与包裹同一份字段的 `InstalledRoute`。
- 完整参数应能表达目标网段、指定接口和有效 metric，以及后端实际操作所需的属性。指定接口不能被隐式替换为 Manager 当前 TUN；缺省接口才使用实例默认接口。
- 输入中的接口名和默认参数在执行前解析。创建成功后保存实际使用的参数，删除不得重新根据当前配置猜测接口和默认值。不同接口/网络作用域的同 CIDR 不是同一条路由。
- 如果确需部分输入与完整值两种形态，可以使用 `optionize` 生成输入类型；只需少量可选参数时不强制引入依赖。后端系统调用使用完整值，不把可选字段散落到删除路径。
- “本次成功创建”由所属集合或资源持有关系表达，不能因 Route 字段齐全或系统已存在同一条目就获得删除权。平台私有参数可以保存在具体后端或 Route 的平台部分，不再复制一套公共路由模型。

这属于路由模型和后端表达能力修正，不要求本阶段额外开发用户配置、RPC 或任意路由修改 API。

## A2：一个 RouteError，成功结果使用 Result / Option

**对应方案：第 3.2、3.3 节。**

删除 `AddRouteOutcome`、`RemoveRouteOutcome`。使用一个 `thiserror` 错误枚举区分 `Failed`（确定未完成）和 `Unknown`（结果不明）。接口可以简化为：

```rust
async fn add(&mut self, route: &Route) -> Result<Option<Route>, RouteError>;
async fn remove(&mut self, route: &Route) -> Result<Option<()>, RouteError>;
```

add 的 Some 表示本次创建并返回实际参数，None 表示已存在、不认领；remove 的 Some 表示删除，None 表示精确目标已不存在。如果没有调用者需要区别 Removed/Absent，remove 直接返回 `Result<(), RouteError>` 即可。

Unknown 仍需保存尚未查明的操作责任，不能当成普通失败反复重发；实现为必要的局部记录即可，不要求沿用当前所有 PendingOperation 类型和表结构。精确目标不存在的确认也不能退化成按前缀猜测。

## A3：生产后端采用编译期选择，删除无必要的动态分发

**对应方案：第 3.3、3.4 节及平台落点。**

已有 `common/ifcfg/mod.rs:164–184` 通过 cfg/type alias 选择具体平台实现。新路由后端沿用这一方式，Manager 直接持有当前平台的具体 Backend，删除生产路径的 `Box<dyn NativeRouteBackend>` 和为它设计的后端搬运接口。

NoTun 在装配处旁路或使用 Option 即可。多个接口、多个网络作用域是实例/参数差异，不是动态分发的理由。测试如确需替换后端，可引入小型泛型接口，不要求生产使用 trait object；也不为测试创建通用插件层。

移动端的整批 VPN 配置确实不同，但本阶段没有生产接入，不提前建立动态 Delegated 分支和模拟会话框架。到真实迁移时再决定对应平台具体后端与宿主适配。

## A4：用 guarden 和资源所有权收束清理，删除默认的冻结交接协议

**对应方案：第 3.4、5.3、5.4 节及 DNS 交接对 Frozen 的依赖。**

“解绑时的循环等待”来自旧方案自身的调度顺序，不是必须增加一套协议才能解决的底层限制。仓库已有 `guarden = "0.3"`：支持显式 trigger 后等待，也支持等待中途被取消时继续调度剩余异步任务。应优先复用。

修订后的清理思路限定为：

1. 运行期间由 Manager 管理成功创建记录；需要退出/换接口时，先停止对对应资源发起新的正常更新。
2. 清理上下文取得相关记录、在途操作及后端/设备所需资源的所有权，用 guarden 承担清理任务的生命周期。正常路径显式触发并等待，等待超时后清理任务继续持有资源并结算操作。
3. 资源释放与清理按明确顺序执行。必须持有真实设备资源或由宿主保证其生命周期；只保存 ifname/ifindex、甚至仅保留后端 socket，都不能阻止设备被提前释放。用户指定的外部接口没有设备所有权时，只做可确认的操作并报告失效，不能假装拥有该接口。
4. 清理完成/失败通过一个实际需要的完成通知回传。guarden 不会自动把删除失败变成成功，也不自动解决本方记录与外部路由的归属。

据此删除作为默认架构的 `FrozenAwaitingDecision`、`CleaningActive`、`ConfirmInterfaceDestroyed`、`CleanupRetiredInterface` 及其全局协调规则。不要给 guarden 再包一层具有同样命令和状态的清理框架。若某具体平台确实无法以所有权和顺序表达某个约束，应在平台接线处给出具体证据和最小补充。

以接口/实例需要的一批资源为清理单位即可，不要求每条路由一个 guard、一个任务。DNS 写入权交接保留必要的顺序和完成结果，但不再依赖 Frozen 协议；不要扩展成通用来源预留系统。

## A5：Legacy 是过渡安排，不进入长期架构

**对应方案：第 1.2、6.1、8、9 节。**

本阶段未迁移的平台保留原有生产链路，要求编译通过且不破坏原功能即可，不提前精做其新后端、模拟会话或完整平台验收。删除以长期公共模式枚举为目的的 `RouteBackendMode::Legacy` 设计；编译条件或装配处的一次选择足以保证新旧 writer 不同时运行。

同步缩减实施批次与验收范围：真实接管的平台完成正确性和性能验证；未接管的平台明确标为后续迁移，不声称“新后端就绪”。禁止为了过编译给新后端返回空成功，保留旧路径即可。

## A6：通知只负责唤醒，不强制另建 watch 体系

**对应方案：第 4 节及 ManagerCommand。**

watch 是 Tokio 已有的最新值通知工具，不是必须选用的架构。允许将刷新通知合并为 `ManagerCommand::Refresh`，Manager 收到后拉取权威输入，不逐条重放路由事件。已有配置 watch 可以直接 select；不要仅为入口形式统一而为每个来源增加转发任务。

选择标准是实际接线更少、稳态更便宜、事件风暴下可合并。若使用有界命令队列：刷新可合并，但队列满不能导致更新永久遗漏；来源不应等待 Manager 完成系统调用，生命周期请求也不能被当作刷新提示随意丢弃。Core 不依赖 Host 的 ManagerCommand，由现有 Core 通知能力或薄宿主接线跨越边界。

不再要求所有来源同时具有一份 ArcSwap、一份 watch 值和专用转发任务。保留权威快照与所需唤醒方式即可；先提交事实再通知、启动先订阅再读取的要求仍保留。

## 修订交付与保留的验收

重写 step2 的接口、生命周期、落点和实施批次，使其主体回到：**一个 Manager、一个完整路由模型、一个具体平台后端、一种路由错误类型，以及 guarden 管理的清理任务。** 文件按实际职责拆分，不以复制全部示意类型或增加模块数量作为进度。

同步删除旧 Frozen/命令形状的验收，改验真实行为：指定接口正确、默认参数解析一致、只删除本次创建条目、输入变化及时收敛、失败退避、Unknown 不误报、超时后结果不丢、清理期间设备资源不被提前释放、同配置换卡仍安装路由、DNS 无双写。通知风暴和实际后端性能测量继续保留。
