# HostRouteManager 第二步方案：收缩后复审

审查基线：`c8c6e7f3`；方案为 [`host-route-manager-step2-plan.md`](host-route-manager-step2-plan.md)，Git blob `4bd27e1a82afff3e12ec2af43ee6943e9a61b514cd`。本文行号均对应此版本。

**结论：简化方向正确，但清理与换卡部分仍需修订后再照此实现。** 统一 Route、一个 RouteError、编译期后端、Refresh 命令和未迁移平台保留旧路径均可保留。以下问题用具体资源持有关系和局部控制流解决，不恢复 Frozen 协议、双路由模型或通用生命周期框架。

## R1 / P1：网卡名称不是一次设备生命周期的身份

**位置：第 99–106、230–231、281–290 行。**

方案用 `current_interface: Option<String>` 判断换卡，并在名称未变时复用缓存。销毁 `tun0` 后再创建同名 `tun0`，名称没有变化，但旧设备上的路由已经消失；旧 installed 仍可与 desired 相等，Manager 因而跳过安装。第 290 行声称换卡后 installed 为空，却没有定义谁完成这次交接。只有 Refresh/Stop 的接口也未说明如何读取或接收新设备资源。

另外，Route 保存的接口仍只是名称。若删除时重新将名称解析为当前接口，记录并非创建时的实际系统目标。支持显式指定接口后，也不能在默认 TUN 销毁时清空整个 installed：其他接口上的路由可能仍然存在。

**最小修正：**

- 保留单一 Route；在它或具体后端的私有记录中保存创建时解析的接口身份及所需作用域，删除不重新按名字猜测。接口名可以继续作为输入和显示信息。
- 在 Host 的真实安装/替换路径明确传递设备资源，并触发对应绑定的替换；即使名称相同也必须执行。可以直接按设备生命周期重建 Manager，不要求引入版本号体系。
- 换卡只处理属于该设备的记录；显式指定其他接口的路由不能因默认 TUN 释放而被当作已删除。

**验证：** 同名 TUN 重建且配置不变时重新安装；默认 TUN 退出时，不丢弃其他接口上尚未删除的记录。

## R2 / P1：guarden 尚未接到真实设备及在途操作的所有权

**位置：第 345–354、370–373、556 行。**

当前守卫只捕获 backend、两份记录和发送端，没有设备资源。现有 `runtime_host/tun_common.rs:60` 的 `TunNicState::stop()` 会取出并释放持有 `NicCtx` 的容器；仅让路由清理任务持有 Netlink socket 无法阻止这条路径释放 TUN。第 372 行据此宣称任务持有完整资源，与示例及现有 Host 接线不一致。

第 373 行又允许 Host 关闭设备、丢弃记录，并断言清理任务不再调用系统接口；已经启动的清理循环并不会因此自动停止。此外，停止新 ADD 不等于处理完已提交的操作：若在途 ADD 在清理记录移交之后成功，可能产生无人记账的路由。

**最小修正：** 给出一段真实 Host 接线，明确谁持有 `NicCtx`、谁等待最后一次在途操作、谁最后释放设备。清理上下文应实际取得所需设备资源，或由持有它的 Host 任务负责等待清理；这段顺序本身也要受 guarden 保护，不能在外层等待超时后先释放设备。单线程循环可以先完成当前操作再进入清理，无需另造任务框架。

若选用“销毁自有 TUN 使关联路由消失”的捷径，应先停止并收束该设备的全部旧操作，确认实际设备销毁后再释放对应记录，不能与逐条删除任务并发执行。外部指定接口不具备这一捷径。

**验证：** 让 ADD 停在等待响应处，触发退出并令调用方等待超时；实际资源仍存活，迟到结果有人处理，旧操作不会落到重建后的设备上。

## R3 / P1：清理示例会忽略 Unknown，也没有保留完整完成结果

**位置：第 351–368、385–393 行；关联第 311–326 行。**

示例捕获 `unknown` 却完全不使用。installed 为空、unknown 非空时仍会发送 `true`，直接违反第 393 行的成功条件。对于此前删除返回 Unknown 的条目，它仍在 installed 中，清理循环又无条件 remove，会违反“未知结果严禁盲目重发”的约束。正常 diff 循环同样需要在执行前排除未决项，不能只写入集合。

删除失败时示例只记录日志，消费并丢弃条目，最终仅发送 bool；调用方无法从这个结果构造所声明的 `CleanupIncomplete`。第 391 行也未明确 JoinHandle 属于哪个任务：Manager 的 JoinHandle 只有在 Manager 等到清理实际完成才返回时，才能代表清理完成；guarden 分离出去的任务不会自动受它追踪。

**最小修正：**

- 清理返回已有的 `Result<(), CleanupIncomplete>`，收集删除失败与未决条目；正常执行和清理均跳过仍未查明的操作，不假设 guarden 能解决系统调用结果不明。
- 写清守卫如何实际运行、结果由谁接收。`trigger()` 返回的异步任务需要被 await/poll 或显式 detach；不能持有未轮询任务却只等完成通知。
- 调用方 deadline 只限制调用方等待；实际清理任务及其最终结果仍由一个明确持有者跟踪。保留一个任务和一份完成结果即可，不需要监督框架或多套通知。
- 删除“绝不在内核留下未决状态”的保证。guarden 能维护任务生命周期，系统调用结果确实无法确认时仍应如实返回未完成。

**验证：** 仅有 Unknown 时不得成功；未知删除不会被再次盲发；删除失败能返回具体未清理条目；stop 超时后仍能取得后台清理的最终结果。

## R4 / P2：平台别名与本阶段交付范围不一致

**位置：第 23–28、182–192、402–403 行。**

方案只交付 Linux 后端，却定义 Windows/macOS 别名指向本阶段不存在的实现，其他平台还要求 Stub。只要这些声明参与编译，未启动 Manager 也不能避免类型解析失败。Linux 仅按 target_os 接管，也没有处理仓库现有的 `linux-netlink`/`tun` feature 边界；例如 `netlink-sys` 是可选依赖。

**最小修正：** 对实际接管的 target/feature 组合启用新模块及装配，其他组合保留现有路径；若决定调整 feature 依赖，应明确写出。删除当前阶段不存在的平台别名和 Stub 要求，并将 FreeBSD、macOS NE 等现有分支列入保留范围。无需为过编译提前实现其他平台后端。

**验证：** Linux 实际接管组合以及现有支持的未接管构建组合能够编译，新旧 writer 的选择与相同编译条件一致。

## 两项收尾修订

- 第 157 行仍用 `async_trait`，泛型静态分发下没有必要为每次调用装箱 future。优先用原生 async trait；需要保证跨线程调度时，在返回 future 上表达 Send 约束。这是局部性能修正，不再增加抽象层。
- master plan 仍有 `RouteSpec → InstalledRoute`，step1 仍示意 `Box<dyn ...>`。按 review-6 的要求，只同步这些被用户反馈替代的接口形状与平台范围，避免下一轮 agent 按旧总纲恢复已删设计；已确认的业务规则不用重写。

本轮仅审查方案并新增本文，未修改设计正文或产品代码，未运行产品测试。已核对 Host 设备释放路径、现有平台 feature 选择及本地 guarden 0.3.0 的 trigger/detach 实现。
