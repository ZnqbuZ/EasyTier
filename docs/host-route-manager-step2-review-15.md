## R1 / P1：接口销毁判定仍沿用上一轮已指出的错误前提

位置：step2 第 37–42、127–130、193 行。

当前仍把“ifindex 改变或丢失”直接解释成“旧设备已销毁”。默认接口从 A 切到 B 而 A 尚存时，这会直接丢弃 A 的安装记录，遗留其路由。文档也没有规定 Host 必须完成旧设备销毁后才能发布这一事实。

另一方面，`DeviceId { ifname, ifindex }` 不能保证区分设备重建。接口 A 销毁后同名、同 index 重建，中间 None 被 watch 合并，Manager 看到的最新值与旧值相等，会认为路由仍在。Linux 允许创建接口时指定 index，不能把它当成永不复用的实例标识。[rtnetlink 的 RTM_NEWLINK 说明](https://man7.org/linux/man-pages/man7/rtnetlink.7.html)

最小修正：Host 事实明确区分设备实例，优先复用已有实例身份，没有则补一个仅用于自身设备重建识别的本地标识；明确销毁事实在实际销毁后发布。只有确认销毁才核销，普通出口变化仍正常撤销旧路由。Manager 保存身份值，不持有网卡资源，也不为此建立版本框架。展示名称不参与路由有效参数的等价判定。

`perform_shutdown_cleanup` 还需明确先重读并处理上述事实，否则“销毁通知与取消同时抵达”的测试没有对应保障。核销只处理确认消失的接口，不能影响外部接口上的记录。

## R2 / P1：平台接管范围和旧 writer 停用条件被一起删掉了

位置：step2 第 24–28、147–153、179–180 行；现有 `virtual_nic.rs:1291`、`dns_server/server_instance.rs:377–388`。

本版只定义 Linux 后端，却无条件要求 DNS 删除原来的路由增删，也没有要求停掉代理路由旧 updater。照此接线，Linux 会有新旧代理 writer 竞争；未迁移平台则可能失去 DNS 路由。

恢复三条短约束即可，无须重新引入 Legacy 枚举或平台空实现：

1. 本阶段仅在实际启用 Manager 的 Linux + `linux-netlink` 装配中接管 IPv4 代理、手工代理和 DNS 路由；不顺带启用 IPv6 代理写入。
2. 同一个接管判定同时停用代理旧 updater 和 DNS 原路由增删。未迁移平台保留两者原路径；No-TUN 不产生原生安装记录。
3. master plan 同步单 watch、后端按网络作用域复用、DNS 提前接管；删除其“当前树无 step2 文件”的过时状态。step1 的业务规则继续有效，迁移顺序以本次明确的范围调整为准。

## R3 / P1：DNS 合并条件错误，可用性确认仍只有结论

位置：step2 第 179–184、196 行；step1 第 133–155 行。

“代理包含 fake_ip，和 DNS 记录为单条安装”不成立。例如代理 `0.0.0.0/0` 与 DNS `7.7.7.7/32` 是两个不同目标；如果合并成一个，关闭代理时可能丢失 DNS 所需的 /32，关闭 DNS 时也可能保留了不该保留的具体路由。

应明确沿用 step1：只有相同目标、适用出口并经既定参数规则合并的需求才形成同一个有效 Route。代理恰好是 `fake_ip/32` 时验证同路由共享；代理只是更宽前缀时保留两条需求，分别撤销。fake_ip 已在 TUN 子网内时不额外产生 DNS /32。不要新增覆盖网段压缩算法。

此外，“成功部署 DNS 配置与路由后才可用”还不是接线方案：本版只有向 Manager 发刷新，没有 DNS 启动方获得处理结果的入口。现有 `MagicDnsServerInstance::new` 原本会等待路由添加结果；删除该 await 后，不能用“刷新已发送”代替成功。

需要补一小段具体启停时序：何时发布需求、怎样得知本次 DNS 所需路由已就绪、初始化失败/取消时怎样撤回需求、停止时怎样结束该需求；DNS 的接口与子网事实须对应当前设备实例，不能把旧实例的异步结果用到新接口。可以在现有 DNS 启动流程使用一次性的完成答复，不需要第二个刷新通道或通用版本等待 API。若不准备提供完成确认，就必须明确采用异步就绪语义，不能保留当前的同步成功保证。

## R4 / P2：external_present 是无失效规则的缓存

位置：step2 第 72、138、141、194 行。

当前只有插入和从 to_add 中排除，没有清理规则。例如：需求 R 存在时发现外部路由，记入 external_present；随后 R 被撤销，外部程序删除路由；再添加 R 时，旧缓存仍阻止 ADD，需求无法生效。这不需要持续系统漂移检测就会触发。

最小修正：每轮将 external_present 限定在当前仍适用的需求与设备上下文内，需求撤销或对应接口销毁时清除观察记录；重新出现的需求重新尝试。不能让这个集合随历史需求增长。若提供显式重新核实入口，也要说明它使哪些观察失效，普通重复唤醒无需清空缓存。

EEXIST 本身也不能证明已有路由的有效参数完全等价。只有确认等价才能记录为满足需求的 external_present；否则记录冲突并按失败规则抑制重复尝试，不认领、不删除、不报告 DNS 就绪。核实属于异常/冲突路径，不要求每次成功增删先 dump。

## R5 / P2：协调循环缺少停止前检查和输入过期检查

位置：step2 第 93–113、140–141 行。

当前先 reconcile 再检查取消；Manager 启动前已经取消仍会进入一次普通协调。取消与刷新同时就绪时，默认 select 也不保证先选取消，新一轮又会进入 reconcile。分批检查只写了取消，没有检查配置或设备事实在 I/O 期间已变化，长批次可能继续下发过时路由。

局部修正即可：循环顶部及发起下一批操作前检查取消；分批同时检查刷新接收端是否有未处理变化，有则结束旧批次并重新读事实。在途操作先收束并记账，不通过取消等待假装系统操作未发生。每轮读取事实之前标记当前通知已读并释放借用，不在 I/O 之后吞掉新通知。[Tokio select 默认分支选择语义](https://docs.rs/tokio/latest/tokio/macro.select.html#fairness)

保持首轮主动协调和统一清理尾段，不增加命令队列。到期失败项按实际截止时间处理，不能因新通知不断推迟重试。

## 实施时保留的简短约束

- `&mut JoinHandle` 的等待方式正确；Host 实际拥有 JoinHandle。任务已完成时消费句柄，避免再次轮询已完成的 future。超时可以再次等待，正常完成后的重复 stop 是否需要支持由真实调用方决定，不引入共享结果缓存。[Tokio JoinHandle](https://docs.rs/tokio/latest/tokio/task/struct.JoinHandle.html)
- 精简正文不等于取消后端约束：固定 table/网络作用域、完整删除参数、请求与 ACK 匹配、I/O 有界等待、Failed/Unknown 区分继续有效。当前底层收 ACK 是阻塞循环，单加 spawn_blocking 不会自动提供这些保证，也不能证明性能最优。连接复用与异步 I/O 的取舍按原生测试和基准确定。
- 测试“稳态无 dump”应限定在正常增删场景；不能禁止 EEXIST 或 Unknown 的必要核实。“多个通知合并”应验证最终事实生效、无重复系统写入，不要求任意调度下恰好只唤醒一次。
- 补回确定失败退避、Unknown 隔离、同槽替换失败不继续添加，以及 step1 业务规则的验证引用即可；不必在本文重复展开全部算法与测试代码。
- 模块数量不是本轮问题。当前模型可以放 `mod.rs`，但无须为了减少一个文件再调整架构。
