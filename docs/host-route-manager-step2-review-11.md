# HostRouteManager 第二步方案：第十一轮复审

审查基线：`5363c6c4`；[`host-route-manager-step2-plan.md`](host-route-manager-step2-plan.md) Git blob 为 `2a9f3b02aebc3d0603cb790a12de963ea2bb1bd2`。本文行号对应此版本。

**结论：上一轮的三项结构性修正已落实，但新增代码仍有两处会虚报清理成功。** 保留目前的设备持有、关闭顺序和局部解绑设计，只修正结果判定及未决记录的处理，不再扩大架构。

## R1 / P1：stop 把“通道关闭且没有结果”判成成功

**位置：第 407–415 行。**

发送 Stop 失败，或 ACK 通道关闭时，代码执行：

```rust
self.query_cleanup_result().await.unwrap_or(Ok(()))
```

`None` 表示尚无最终清理结果，不表示清理成功。Manager 异常退出、在结果发布前丢弃 ACK，或者取消路径先关闭接收端时，都可能到达这里；此时返回 Ok 会掩盖未完成的路由清理。它直接违反第 759 行“仅当无失败且无未决项时成功”的条件。

**最小修正：** 只有已保存的 `Some(Ok(()))` 才能返回成功；有确定结果就返回该结果，没有结果则返回 `CleanupIncomplete`，或在同一 deadline 内等待实际完成。不要把通道关闭本身当作完成证据，回退查询/等待也不能脱离 deadline。

Stop 入口还会先取消 token，再发送命令。取消分支必须进入与 Stop 相同的清理及结果发布路径，不能直接退出；第 720 行“未入队意味着 Manager 未开始停机”也应据此修正。无需增加第二套停机机制。

**验证：** Stop 发送端或 ACK 关闭、cleanup_result 尚为 None 时不得返回成功；已有最终错误时原样返回；已有最终成功时重复 stop 可以成功。

## R2 / P1：局部解绑漏掉未决 ADD，重复解绑还会绕过上次失败

**位置：第 568–573、579–592、614–629 行。**

局部清理只遍历 `installed_routes` 分出的 device_routes，再从这些条目里检查 unknown。可是 ADD 返回 Unknown 时，条目只进入 `unknown_routes`，并不进入 installed（第 512 行）。因此存在直接反例：

```text
installed_routes = {}
unknown_routes   = {旧 TUN 上添加结果不明的路由 R}
unbind → device_routes 为空 → 两个结果 Vec 都为空 → 返回 Ok(())
```

R 仍留在 Manager 的 unknown 集合里，后续 stop 又会报告未完成。同一个责任在解绑时被判成功、停机时又被判失败，结果不一致。

另一个入口是重复解绑：第一次删除失败时，代码保留失败/未决记录，但已经 take 当前设备并 drop；第二次 unbind 进入 `None => Ok(())`，不再检查前一次尚未解决的结果。第一次 ACK 超时后重试同样可能掩盖该错误。第 628 行“记录仍在集合中”不足以保证调用方能取得真实的解绑结果。

**最小修正：**

- 独立按旧设备筛选 unknown 集合，包含添加结果不明的条目，再合并本次删除产生的 Unknown；不能只从 installed 反查。
- 统一“已确认销毁自有非持久设备”与旧记录的结算规则。如果销毁已经足以确认该设备的路由全部消失，就在该次解绑中一致地结束对应记录的责任；如果仍判为未完成，则保留并返回该次结果，重复调用不能仅因 current_tun_device 为 None 就改报成功。
- 原调用方超时后，仍应能取得该次解绑结果；保留一份局部完成结果或继续观察原完成等待即可，不需要版本、历史或通用任务框架。

**验证：** 仅存在未决 ADD；删除失败后再次解绑；第一次 ACK 等待超时、后台最终失败后再次获取结果。各场景必须保持记录与返回结果一致，同时不把其他接口的 Unknown 混入默认设备解绑结果。

## 上轮问题状态与实施边界

- Host 先停止并 join 转发任务，再由 Manager 释放保活描述符：上一轮关闭顺序问题已关闭。
- 入队和 ACK 等待共用绝对 deadline：上一轮解绑入队无限等待问题已关闭。
- 解绑分支借用 backend、保留其他接口并继续主循环：上一轮局部清理与停机混用问题已关闭；本轮仅修其结果和记账细节。

方案无需继续整体扩写。修正上述分支并补对应验证即可；串行循环中的 `flush_in_flight()` 不应被实现成新队列框架，Stop 中无人使用的额外 completion 通道也可直接删除。

本轮仅新增审查文档，未修改方案正文或产品代码，未运行产品测试。判断依据为当前方案的具体分支及已定义的记账规则。
