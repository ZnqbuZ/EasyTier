## T1 · P1：deadline 仍未覆盖命令等待与停机清理中的删除调用

**位置：方案第 291–294、396–399、465–477 行。**

Stop 通过命令通道进入同一个协调循环。如果循环正等待 add/remove，Stop 命令可能尚未处理，便无法进入第 468 行的 timeout。即使已进入停机流程，第 473 行只在每步检查时间，之后发起的 remove 仍可能无限等待。给“停机开始时已有的那个操作”加 timeout，不等于给整个 stop 设置 deadline。

此外，超时后保留 Manager 的 JoinHandle 并不自动保留它内部那个系统操作的结果接收路径；必须明确该操作仍由谁等待并记账，不能超时丢弃其结果接收句柄后只观察外层任务退出。

**修改要求：** 从 `handle.stop()` 入口起，发送/等待命令确认、等待已有操作、等待每次清理操作都受同一个 deadline 约束。Manager 独占在途操作及结果接收句柄，调用方超时只结束等待，不取消或脱离该操作；任务完成后照常记账，Host 能继续取得最终清理状态。明确循环等待 I/O 时仍能响应停止，或由 handle 的限时等待独立返回“尚未完成”，不要要求 Stop 必须先被循环取出才开始计时。

**验收补充：** 分别阻塞 Stop 发出之前的 add、Stop 开始之后的 remove，以及命令确认，三种情况都按 deadline 返回；随后释放操作，验证最终结果仍被原 Manager 接收并正确清理。

## T2 · P1：解绑 ACK 允许 Host 销毁接口，但 Manager 随后仍会发起旧接口删除

**位置：方案第 397、403–406、444–450 行。**

第 447 行承诺收到 unbind ACK 后无后台悬挂 I/O，Host 可以安全关闭旧设备。但主循环下一步立即遍历 retired 后端发起删除。于是可以出现：Manager 发 ACK → Host 关闭旧接口 → Manager 对旧 ifindex 发删除 → Host 稍后发送销毁确认。软件 generation 不会传进内核，也不能阻止接口身份复用时旧操作碰到新设备。

“发送 ACK 时没有在途操作”不足以授权销毁，还必须保证之后不会再开始旧绑定 I/O。当前清理顺序和 ACK 含义不一致。

**修改要求：** 选定一个明确的交接顺序：要么完成旧清理后才给可销毁 ACK；要么 ACK 前停止旧绑定的一切新 I/O，保留记录等待 Host 的销毁确认，只有 Host 明确保留旧设备并交回控制后才恢复清理。清理失败可以报告未完成，但不能同时授权 Host 销毁和允许 Manager 自主发起旧操作。只需要在已有生命周期路径中明确这个顺序，不需要新的通用所有权框架。

**验收补充：** 用屏障控制 ACK、设备关闭、销毁确认的先后，验证从“允许销毁”的 ACK 到销毁确认之间，旧后端调用数为零；保留设备的清理路径另行验证。

## T3 · P1：新接口绑定没有使执行缓存失效，输入不变时可能永远不重装路由

**位置：方案第 309–311、368–374、410–419 行。**

快速路径只比较 peer、manual 和未迁移事实，不比较当前绑定，也没有要求 BindInterface 强制一次协调。可复现的计划执行序列是：旧接口已安装 P → 解绑并确认销毁，retired 清空 → 同地址新接口绑定，installed 为空 → peer/manual/DNS/网段均未变且无重试 → 第 416 行直接休眠。后续低频核对仍看到相同输入，P 不会重新安装。

这也说明“无需重新计算 desired”和“无需执行 desired 与 installed 的差异”不能用同一个输入缓存条件判断。

**修改要求：** 新绑定建立时强制执行一次协调，可以复用旧 desired 而不重算业务投影。快速跳过执行必须同时满足当前绑定已完成协调、没有尚未执行的差异、没有到期重试或清理工作。用一个实际需要的 dirty 标记或等价控制流即可，不必增加版本体系。

**验收补充：** 输入和地址完全不变，仅替换 TUN，验证无需新 peer/config 通知就能在新接口安装全部期望路由；另覆盖先有输入、后由 DHCP 首次建卡。

## T4 · P1：DNS 交接仍有两条把“没有成功记录”误当成“已清理”的路径

**位置：方案第 504–507、516–526 行。**

1. **未决添加放行。** 添加 P 返回 OutcomeUnknown 后，installed 里没有 P，也没有仍在执行的操作；第 517 行的“从未安装且无在途操作”就可能发放预留确认。但 pending 中仍有可能已生效的添加，DNS 此时不能被授权接手。交接条件需要检查同一绑定/冲突范围内的 installed、pending 和 in-flight，而不只是前两项中的成功记录及当前 I/O。
2. **DNS 删除根本未执行。** 当前 `server_instance.rs:433–447` 把路由删除放在 `if let Some(system_config)` 内；同文件 `get_system_config` 在 Linux 返回 None，而路由添加 `:377–388` 不依赖 system_config。只按本文把 `let _ = remove...` 改成错误传播，Linux 仍会跳过删除并可能返回 Ok，随后 Tracker 提前释放范围。此问题已在上轮指出，本轮修改要求仍遗漏了条件调整。

**修改要求：** 预留确认必须排除未决副作用；无法核实则保持阻塞。DNS 路由清理与系统 DNS 配置恢复分开执行，依据本次实际路由责任决定是否删除，不能由 system_config 是否存在决定。返回 Ok 必须表示应清理的路由已删除或确认不存在；系统 DNS 恢复失败也不能让必要的路由清理被提前返回跳过。

**验收补充：** 添加结果不明后 DNS 请求同一 P，不能收到放行确认；Linux `system_config=None` 且本次实际安装了 DNS /32 时，停止仍须执行路由删除，失败继续保留排除范围。
