## S1 — P1：超时/恢复仍按“条目存在”补记归属，计划更新也缺少前置状态核验

**位置：** 修订版第 283、405–408 行。

第 408 行规定：操作超时后读回，只要路由存在就“按成功推进状态并补记归属”。这直接绕过第 284 行的 ExternalSatisfied 规则。第 406 行也把接口绑定证据与符合 Desired 作为补记 Commit 的条件；接口归属不能证明该路由由这次操作创建。

**反例：** 扫描时 R 不存在；本方记录 Add Intent 并发起操作；外部先创建了相同的 R，本方调用实际返回 AlreadyExists，但响应丢失。重新扫描看到 R，当前规则会认领外部资源，随后在退出时删除。

同一段把所有“底层操作超时”都按存在处理，未区分 Add、Delete、Replace。Delete 超时后条目仍存在，不能作为成功证据。

第 283 行的“处于待修改流程则 Replace”也不足以证明差异属于本方：本方计划从属性 A 改为 B，同时外部将实际条目改为 C，此时不能仅因有 Pending 就覆盖 C。

**修改要求：**

- 统一所有正常、超时、恢复入口的归属准入规则，不能让故障分支降低证据要求。
- 按 Action 定义核对结果；分别核验最后确认的前态、操作目标后态和当前观察态。存在/不存在、结果已达成与“由本方创建”是不同结论。
- 无已确认创建结果、有效历史归属或明确独占/接管授权时，保留 OutcomeUnknown/ExternalSatisfied/UncertainExternal；不补写“本方创建”凭据。
- PlannedMismatch 只能在操作前置状态仍可验证且满足授权的情况下继续；遇到第三种属性或无法区分的替换应进入冲突/不确定分支。没有原子条件操作的平台须说明外部协作假设。

**验收：** 外部抢先创建导致 EEXIST 丢响应；Delete 超时但条目未删；Replace 中途外部改为第三种属性；Intent-only 重启恢复。

## S2 — P1：共享引用计数只比较槽位键，会合并转发含义不同的需求

**位置：** 第 208、215–216、266–273、346–349 行。

第 347 行规定相同 RouteIdentity 即共享引用计数，但第 267 行给出的 Linux Key 不含出口接口或下一跳。即使把它视为当前支持范围内的冲突槽位，也不能证明两个需求可由同一条路由满足。

**反例：** 实例 A、B 都需要相同的 DNS `/32`，table/metric/TOS 相同，分别要求送入 tunA、tunB。按文档 Key 相等，计数为 2；实际只写入指向其中一个接口的路由，却可能向两个实例报告满足。Windows 相同 Key 下的不同 metric 需求也不能只做计数而忽略属性分歧。

此外，第 208 行把 metric 和 NextHop 一概放进身份，第 267–269 行又分平台定义，第 273 行再用统一的“相同 priority、相同表”描述冲突，三者并不自洽。Windows 同一 DestinationPrefix + Interface + NextHop 不会仅因 metric 不同就获得第二条独立路由，见 [CreateIpForwardEntry2 官方文档](https://learn.microsoft.com/en-us/windows/win32/api/netioapi/nf-netioapi-createipforwardentry2)。

**修改要求：** 分开平台对象定位键、操作匹配条件和需求等价性。共享必须同时满足相同域、有效绑定、规范化转发语义和兼容属性；只占用相同槽位但要求不同出口/属性时，按明确的业务冲突策略处理。快照的重复提交不能重复增减引用，计数应由有效来源集合派生。平台键按地址族/支持范围验证，不能把简化键当全平台定理。

**验收：** 同键不同 TUN、同键不同 metric、同资源重复快照、两个来源之一撤销。只有真正等价的需求可以合并。

## S3 — P1：接口索引复用时完整属性相同仍不能证明是旧资源

**位置：** 第 225–231 行。

第 226 行将“属于 Owned，且在历史台账中或属于当前代际”写成删除的充分必要条件；第 229 行又试图通过完整 RouteIdentity 比较防止复用误删。这些都不能区分两个生命周期中配置完全相同的条目。

**反例：** gen=1 接口销毁后，gen=2 使用相同名字、ifindex、前缀、metric 和下一跳。旧台账仍有 R；新的 R 恰好与旧记录所有系统属性一致。按该规则旧清理任务会删除新路由。即使新路由也是 EasyTier 创建的，它也不能由旧代际任务擅自撤销。

**修改要求：** 历史台账仅证明存在清理责任，不证明当前对象仍是旧对象。删除前需要可验证的绑定连续性/操作前置条件、无当前需求及在途操作冲突，以及平台允许的身份精度。原接口已确认销毁时，终结对其强绑定对象的旧清理责任；身份复用且无法区分时进入不确定分支，不按相同属性删除。规则等非接口绑定资源另按自身作用域处理。重写删除谓词，不能用 `iff` 把归属和代际条件当作完整授权。

**验收：** 接口销毁后相同 ifindex + 完全相同属性重建；旧清理与新 Add 交错；迟到 Add 与当前需求重叠；原接口确认消失而规则仍残留。

## S4 — P1：超时退出后无条件释放租约，可能让旧执行者与新执行者同时写入

**位置：** 第 362–384 行。

顺序图要求“终止并排空所有 Pending”，然后释放独占租约，并返回 Success/Incomplete；超时时只把资源记入台账。平台操作不一定能取消，因此“返回 CleanupIncomplete”和“旧执行者已经不能产生副作用”不能等同。

**反例：** 委托 VPN 配置请求或阻塞的后端 worker 尚未结束；shutdown 到期后释放租约。新实例获得租约并配置 B，旧操作此后才应用 A，覆盖新状态。落盘台账并不能阻止仍活着的旧执行者。

**修改要求：** 区分停止接收、停止排队执行、已发请求结果不明、执行者失去写入能力、资源清理完成、允许交接这些条件。无法 fence/cancel/drain 时，返回 Incomplete 可以有截止时间，但不能无条件释放允许新写入者接管的资格；可由仍存活的协调器保留隔离/租约直至安全交接。进程崩溃后的接管须先处理日志中的不明操作，并在委托宿主使用宿主实际验证的会话/epoch，不能只在本方忽略旧回调。

**验收：** 阻塞操作超出 shutdown 时限、旧 Android apply 迟到、新进程尝试接管、日志持久化成功但执行者仍活跃。

## S5 — P1：第二步所依赖的撤销/订阅/版本契约仍未定义完整

**位置：** 第 344–349、388–397、421–422 行。

第 8.1 节虽名为“来源撤销”，仍只有完整快照、异常状态和引用计数，没有定义撤销版本记录如何保留。第 422 行单说 epoch/revision 双单调，不能防止来源被删除后旧快照复活。也没有规定取得初始快照与开始订阅之间如何保证不漏更新。

对外 `wait_convergence(version: u64)` 还没有说明 version 属于哪个来源、哪个实例或域。多个来源各自的 rev=5 不是同一版本；无关来源更新是否使等待 Superseded 也未定义。

**修改要求（仅冻结语义，不要求现在实现）：**

- 给出来源身份、注册 epoch 的分配/失效规则、撤销后的拒绝旧消息规则；明确新进程/重新注册不会重用可被旧消息混淆的身份。
- 规定重复 `(epoch, revision)` 的幂等行为，撤销与暂不可读的区别。来源永久消失的生命周期责任必须确定。
- 提供“初始快照 + 后续更新无遗漏”的契约，具体可用原子订阅或带 revision 的重新核对实现。
- 对外等待使用明确的来源 token、实例提交 token 或聚合版本；说明覆盖范围、Superseded 条件和混合 Verified/HostConfirmed 的完成判定。

**验收：** rev=10 撤销后 rev=9 迟到；来源重启时旧 epoch 回调；初次订阅窗口更新；两个来源同 rev；无关来源更新不错误终结等待。

## S6 — P2：LAN 优先、冲突状态和外层绕行的要求相互冲突

**位置：** 第 272、317–318 行。

第 317 行明确 LAN 优先，第 272 行却把外部高优先级路由选中一概标为 `TrafficHijackedConflict`。正常保留物理 LAN 路径会被自己的规划器报告为劫持；仅靠 metric 也不足以决定跨前缀、跨规则的实际包路径。

第 318 行将“必须 socket_mark + 更高优先级 rule 走 main”作为绝对防环机制，覆盖面不成立。当前 `easytier/src/socket/fake_tcp/mod.rs:440` 明确说明 mark 只作用于 decoy socket，不覆盖真实 FakeTCP 载荷。main 内还可能有兼容模式或其他实例的 TUN 路由，选择 main 本身不是物理绕行证明。

**修改要求：** 将期望的路由对象已安装、策略允许其他路由优先、意外抢占分开。LAN 重叠优先属于需要明确范围及兼容影响的产品策略，不是所有场景下的默认公理。外层绕行应冻结可验证的包路径要求，把 marks、接口绑定及其他机制留给后端/传输能力适配；未覆盖的 transport 不能被宣称绝对防环。

## S7 — P2：部分迁移事实仍错误，矩阵的“已验证”缺少可追溯依据

**位置：** 第 71、85、110–118、327–336 行。

- **Android 事件消费者被误写成界面刷新。** `easytier-gui/src/composables/event.ts:88` 收到 `ProxyCidrsUpdated` 后实际调用 `onNetworkInstanceUpdate`，触发 VPN 配置核对；`event_lagged` 同样触发。不能把这条控制链仅保留为 UI 通知。
- **DNS 分支调用仍无源码依据。** 第 71 行新增断言 `ProxyCidrsMonitor` 读取 `dns.addresses()`；在标注的 `feat/dns-policy` / `2569f35f` 的该文件中没有这段逻辑，只有手工路由、peer CIDR 与 VPN portal 客户端网段。需要找到真实来源或标为待查，不能用一个不存在的调用补齐迁移清单。
- **旧任务停止描述仍不准确。** 第 85 行写 `tasks.shutdown()`，主线 `virtual_nic.rs` 中没有该调用。问题是缺少路由清理协议，不应把未调用的方法当事实。
- **观测链引用定位错误。** `collect_public_ipv6_tun_routes` 位于 `public_ipv6_provider/linux.rs:523`，不是文档反复链接的 115 行。
- **平台测试证据未列出。** “已验证 Windows 基础增删”“已验证 macOS/FreeBSD CLI”应附测试/CI 记录、环境和基线；静态看到接口调用只能证明代码存在。
- **支持范围与最终目标未完全确定。** macOS NE、WASI/嵌入宿主未入矩阵；macOS/FreeBSD 只列“阶段性保留 CLI，预留接口”，没有交代在本轮最终验收时采用何种能力及限制。用户要求架构和可靠性优先，不能以预留扩展点代替最终目标决策。

**修改要求：** 根据实际调用链修正，区分代码事实、推断、目标及已运行验证；不存在证据的地方明确待核实。

## S8 — P2：持续更新下只等待“最终稳态”，可能永远不执行

**位置：** 第 423–424 行。

“防抖 50ms、只对最终稳态规划”若每次更新都重置截止时间，在每 20ms 更新一次时永远不会启动规划。不相关 peer 变化也可能阻塞已稳定 DNS/接口路由、失败重试和退出任务。

**修改要求：** 冻结有界延迟与公平性：合并可覆盖的中间快照，但设置最大等待时间/处理预算；允许基于最新可用快照推进，不能要求整个域先静默。重试、观测修复和退出屏障不能被高频来源饿死。具体窗口数值留待测量。

**验收：** 持续更新超过数个最大等待周期时仍执行；一个高频来源不阻塞另一个稳定来源；停止请求在事件风暴中按约定返回。

## 下一轮修订边界

保留已经修正的分层、manual_routes 作用域、稳定域、非必需 protocol 和显式前缀来源，无需重新展开这些内容。集中修正 S1–S5 的执行前提与来源协议；S6–S8 明确策略、事实和进度保证。不要仅修改总结区的勾选，正文中的操作规则与故障分支必须采用同一套条件。

这些问题都是本步骤应约束的对外行为；具体日志格式、平台调用代码、锁类型和队列实现仍留给后续详细方案。
