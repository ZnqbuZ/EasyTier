# HostRouteManager 新路线 step1 审查

对象：`2cccea53` 的 `host-route-manager-step1-audit-and-contract.md`，文件 Git blob 为 `c5200a2263f262b81210db0b07c192e78cf906af`。

**结论：架构方向符合新总纲，但以下 6 项需修正后再作为 step2 的实施依据。** 不需要恢复 Registry、提交 token、日志或通用状态机；本轮意见针对简单 Manager 自身的操作语义和现有代码事实。

## N1 · P1：不能把现有删除接口直接视为精确删除

文档位置：第 178 行、第 297–299 行；源码：`easytier/src/common/ifcfg/netlink.rs:366–386`。

文档承诺仅删除自己安装的条目，但计划直接复用现有 `remove_ipv4_route(name, address, prefix)`。Linux 实现枚举路由，仅匹配 destination、prefix 和 ifindex，删除第一条匹配结果；没有匹配添加时的 table、metric 等参数。

反例：同一接口、前缀下已有外部 metric=100 的路由，Manager 成功创建 metric=65535 的路由。安装记录正确也不能保证旧删除方法选中自己的条目，可能删掉外部路由。这是当前参数匹配不足，不涉及复杂的外部删除重建识别。

**最小修订：** 把“补齐后端删除匹配参数”列为复用前提，按创建时的完整有效参数定位；无法精确定位时返回错误。增加同接口、同前缀、不同 metric/table 的删除测试，不需要新增归属框架。

## N2 · P1：接口重建与 stop 不能无条件丢弃失败记录

文档位置：第 204–215 行、第 304–305 行。

接口崩溃、失效或更名不等于已确认所有旧路由消失。文档目前要求收到销毁事件就清空旧记录；stop 则在删除失败只打警告后清空记录并正常退出。这与第 292 行“删除失败不丢责任”矛盾，也使“退出无残留”的验收无法成立。

**最小修订：** 新接口单独开始安装记录，旧记录仅在删除成功或已确认由接口销毁收回后释放。停止时先等待正在执行的操作完成并记账，再清理；不要直接 abort 一个可能已产生系统副作用的操作。删除失败保留未清理项并由 stop 返回失败/剩余项，允许退出但不报告清理成功。该信息可仅保留在内存及返回值，不要求持久化。

相应验收分为成功清理和清理失败可见两个场景，去掉无条件“系统路由表干净无残留”的承诺。

## N3 · P1：分来源迁移不代表实际路由互不重叠

文档位置：第 254–258 行、第 272 行。

阶段一假定 Proxy 与尚未迁移的 DNS/显式前缀互不重叠。例如用户手工路由可以正好指定 DNS fake IP 的 `/32`，也可以等于 macOS/FreeBSD 的接口前缀。此时停掉 proxy updater 并不能保证同一实际条目只剩一个 writer；DNS 停止或 NIC 清理仍可能删除另一方需要的路由。

同时，停掉旧 updater 并不等于旧安装条目已经移交。新 Manager 从空安装记录开始，遇到旧条目的 AlreadyExists 又按第 298 行不认领，将无法负责这些条目的后续撤销。

**最小修订：** 按实际重叠条目一起交接相关 writer，或在第一阶段明确排除这些交接场景。明确旧路由的处理：选择干净实例启动切换，或由旧 writer 确认清理后启用新 writer；不能自动认领旧缓存。新总纲已经给出“不同来源映射同一实际路由时一起交接”的要求，应在此保留。

## N4 · P2：No-TUN 空操作成功会制造虚假安装记录

文档位置：第 86 行、第 180 行、第 184–194 行。

No-TUN 的 add/remove 返回 Ok 后，通用循环会把未安装的路由写入 installed_routes。用户未启用 TUN 可以是正常配置，但不能把“无需执行”与“实际安装成功”合并。

**最小修订：** No-TUN 正常计算后跳过执行分支，保持安装记录为空；不必报错，也不必另建状态协议。平台不支持某个操作则明确报告不支持，不能复用空成功后端掩盖。

## N5 · P2：委托后端没有与协调循环、停止流程对接

文档位置：第 165–179 行、第 189–194 行、第 213 行。

接口声称移动端只实现 apply_routes，但 trait 同时要求 add/remove，主循环和 stop 也只调用逐条方法。照此实施，委托后端要么无法实现接口，要么再次用空 add/remove 冒充成功。原生 apply_routes 的默认实现仅接收 desired，也没有说明从哪里取得旧集合及如何回传部分成功。

**最小修订：** 保留明确的两个执行分支：原生逐项应用、逐项记账；委托端完整提交并在宿主确认后更新已应用集合，失败不记为成功。委托端退出采用宿主清理/关闭会话路径。用一个 enum 或很小的接口即可；删除没有实际状态来源的“默认增量实现”，不要求两类后端都实现虚假的逐条方法。

## N6 · P2：复用表仍以已经不在当前树中的旧 step2 为基线

文档位置：第 108–112 行、第 123 行、第 237–245 行。

在当前 `2cccea53` 源码树中，没有 `easytier-core/src/route_demand`、`PeerRouteInput`、`PublicIpv6Snapshot` 或 `subscribe_host_route_inputs`。这些来自此前审查过的旧 step2 提交，不能描述成当前可直接调用的接口。

当前真实入口包括 `Route::list_proxy_cidrs`、`list_proxy_cidrs_v6`、`list_public_ipv6_routes`、`get_my_public_ipv6_addr`；纯覆盖函数还在 `gateway/proxy/cidr_monitor.rs`。需一致读取时可增加一个局部读取方法，不必恢复整套旧框架。

**最小修订：** 明确当前源码基线，分开列“当前存在”“从旧提交选取”“待新增”。若选择恢复旧快照实现，不能称其已具备正确的原子提交保证；此前 step2 审查指出的并发发布问题仍须处理。

顺手修正几处事实/规则表述：

- 旧 PublicIpv6Snapshot 的 lease 是 `Option<Ipv6Inet>`、routes 是 `BTreeSet<Ipv6Inet>`，不是本文给出的 CIDR 类型；必须保留本机具体地址信息。
- FreeBSD 目前共用 `darwin.rs` 的 `MacIfConfiger`，没有文中所述独立 `FreebsdIfConfiger`。
- Windows DNS 路由现有 cost=4（`dns_server/server_instance.rs:379–387`），应在保留规则中写清楚。相同目标不同 metric 不会被 BTreeSet 自动去重；应明确选择或报冲突，不把集合类型当作业务决策。
- 第 287 行把 IPv6 proxy 安装加入验收，但现有 proxy writer/手工覆盖规则是 IPv4。应明确本轮维持该范围，或把新增 IPv6 proxy 支持及其覆盖规则列为明确的功能变更；“模型支持双栈”不自动意味着开启新代理行为。
