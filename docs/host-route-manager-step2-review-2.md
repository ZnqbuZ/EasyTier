## S1 · P1：OutcomeUnknown 只有枚举，没有保存未决操作；停机仍可能误报成功

**位置：方案第 178–190、235–248、365–381 行。**

添加返回 OutcomeUnknown 时可能已经创建了系统路由，但它不属于 installed，也没有对应的未决操作记录。随后 desired 撤销、接口解绑或调用 stop，现有算法只检查当前/旧绑定的 installed：两者可以都是空的，于是第 380 行允许返回 Ok。错误枚举上的“报警阻塞”注释不能阻止这条路径。

**最小修订：** 明确保存未决操作的类型、目标、绑定与实际请求参数，并将其带入换绑和停机结果；不得因 desired 消失而丢弃。可以用后端或 Manager 的小型局部记录，不需要历史日志。未决添加不能作为 Created，也不能靠查到同前缀条目就认领；无法核实归属时允许明确报告阻塞，但不能重发、擅自删除或返回清理完成。补充“添加副作用已发生、确认丢失、随后撤销需求并停止”的测试。

## S2 · P1：stop 的 deadline 没有覆盖等待中的系统调用，返回后也没有可用的跟踪持有者

**位置：方案第 251–265、373–381 行。**

第 375 行先无条件等待在途操作，第 378 行才检查 deadline；清理循环中某个 remove 卡住时同样无法检查。因此它不是有界的 stop。把同步 I/O 放入 spawn_blocking 并不会自动解决等待超时。

同时，`stop(self, ...)` 消费唯一 handle，错误只带 InstalledRoute 列表和字符串，示意 JoinHandle 的输出也是 `()`。本文虽要求“宿主保留在途操作跟踪”，却没有说明宿主还能持有什么对象来等待结果、继续清理或判断何时可启动替代 writer。

**最小修订：** 区分“调用方等到 deadline 返回”和“持有系统操作的任务结束”。可让 Host 保留 handle、stop 使用可复用借用，或在未完成结果中返回继续跟踪的具体句柄；选一种即可。超时不得取消已开始的系统操作，原任务继续接收结果并记账，Host 在释放 NIC/重启 writer 前仍能查询或等待它。测试让 add/remove 保持未完成超过 deadline，验证按时返回未完成状态，之后完成操作仍能正确记账。

## S3 · P1：解绑后的清理被“无可用绑定”挡住，接口交接可能互相等待

**位置：方案第 259–261、320–321、350–361、423–424 行。**

unbind 后，current_binding 为空、旧条目进入 retired_bindings；但主循环第一步遇到无绑定就挂起，无法执行第 358 行的“下一轮”旧责任清理。场景 C 又要求清理或销毁确认后才允许向新接口下发，容易形成清理等绑定、换绑等清理的循环等待。

此外，bind/unbind 都是同步返回 `()`，没有说明怎样把后端交给唯一 Manager 任务，以及 Host 如何获知解绑已处理、在途操作已经结束、旧设备可释放。Notify 只能唤醒，不能完成这类资源交接。

**最小修订：** 将停止、未决操作和 retired 清理放在当前绑定就绪检查之前；无新绑定只暂停新的安装。为实际生命周期交接提供一个有界传递与确认路径，例如小型命令加 oneshot 应答，明确每个确认代表哪个阶段；不扩展成通用命令框架。设备销毁确认也必须对应旧绑定。补充 unbind 后长期无新接口、旧删除先失败后成功，以及 Host 等待解绑后释放 NIC 的测试。

## S4 · P1：DNS 反向交接假定存在“删除确认”，当前清理链路会吞掉失败

**位置：方案第 414–422、502–511 行。**

方案要求 DNS 清理确认后释放预留范围，但当前源码不具备这个确认：

- `dns_server/server_instance.rs:433–445` 的 `clean_env()` 返回 `()`，删除使用 `let _ = ...` 忽略结果，且整段路由删除放在 `system_config.is_some()` 条件内。
- `dns_server/runner.rs` 的清理/任务返回也没有携带路由清理结果。
- `runtime_host/magic_dns.rs:62–65` 等待任务时忽略结果。

因此“DNS 任务退出”不能作为“路由已删除”的确认；照现有 Batch 4 文件清单接线，会在删除失败时提前释放范围。新增 Tracker 本身不能修复这一点。

**最小修订：** 将实际 DNS 启停、runner 和路由清理结果传递列入同批变更，明确失败时仍保留排除范围，并由实际持有者负责重试/报告；无法确定删除归属时不得认领外部路由来清理。预留确认还需覆盖“Manager 从未安装 P”以及“P 正在添加”的情况：前者确认本方无冲突操作即可，后者先结算在途结果，不必为了确认去删除未知系统条目。macOS/FreeBSD 显式前缀也要有对应的过滤与交接落点，当前 6.2 只具体描述了 DNS。

如果给旧 writer 添加这套过渡协调比迁移更复杂，可以将冲突路由的写入职责同批交给 Manager；这是减少临时机制的选项，不要求扩大到整个 DNS 服务重构。

## S5 · P2：输入表仍没有确定可复用快照入口，并让 Core 指向 Host handle

**位置：方案第 34–40、279–300 行。**

读取接口仍写成 `list_proxy_cidrs() -> BTreeSet`“或其快照”，快速路径却要求取得稳定的 `Arc<BTreeSet>`。没有确定由谁保存该快照，实际实现仍可能每次 collect 后包 Arc，无法获得所声称的跳过效果。仅缓存旧指针也不能在“不拉取”的情况下知道权威值已更新。

通知表要求 OSPF 提交处调用 Host 的 `RouteManagerHandle::notify_change()`，与 Core/Host 单向依赖不一致。可以通过已有通用通知能力跨边界，但本文尚未确定。所列 `rebuild_route_table` 也不是当前源码入口；现有的是 `peer_ospf_route.rs:2817` 的 `update_route_table`，还需核对实际代理前缀提交边界。

**最小修订：** 选定一个 Core 自有的只读快照和订阅接口，例如提交后的不可变 Arc 加 watch，由 Manager 直接监听；Core 不认识 RouteManagerHandle。写明在真实提交边界更新缓存后通知，并保证业务提交不会倒退。Manager 每次只读取廉价权威快照以比较，未变才跳过投影；配置比较路由相关字段，避免无关服务配置变化重算。把这些文件与提交顺序纳入实施批次，不再保留互不等价的接口选项。

## S6 · P2：平台表保留旧链路，迁移步骤与验收仍要求全局停旧

**位置：方案第 20–25、394–401、540 行。**

平台表允许 Windows/macOS/FreeBSD 未启用新后端时维持旧链路，移动端明确保留生产旧链路；但第 6.1 节无条件禁用旧事件/updater，最后又要求“全仓代理路由仅由单一 HostRouteManager 负责”。按前者实施不满足后者；按后者停用全部旧路径则超出已列平台接管范围。

**最小修订：** 定义一次确定的生产后端选择，其结果同时控制新 Manager 启动和旧 writer 停用；两者不能分别设置造成漏写/双写。完成门槛改为“本阶段启用的平台/实例已完成接管”，明确其他生产链路保留至第三步。Windows/macOS/FreeBSD 的“后端就绪”需与实际实施任务、验证程度一致，命令状态码测试不能代表精确删除已验证。

## 两处非阻塞事实校正

1. 第 434 行又写成旧 monitor 每秒都会 collect，这不符合 `cidr_monitor.rs:165–176`：它比较 peer 更新时间和配置快照，未变会 continue。应写为每秒检查变化，发生相关检测变化后才重新构建集合；据真实基线测收益。
2. 第 228、449 行的 O(1) 只宜表达单条删除请求数量恒定、取消用户态全表扫描，不能概括内核删除耗时。
