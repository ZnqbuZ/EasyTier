## T1 — P1：崩溃恢复仍可认领外部条目，Delete 超时后的身份判断也不安全

**位置：** 被审文档第 274–285、425–428 行。

第 426 行仍规定：只有 Intent 没有 Commit 时，凭 InterfaceBinding 证据和符合 Desired 就补记 Committed。这正是上轮 S1 已指出的漏洞，与第 281 行的新规则直接冲突。接口是本方创建的，并不能证明其上的每条路由都由本方创建。

**反例：** 本方持久化 Add Intent；外部先创建相同条目；本方 Add 返回 EEXIST，但在记录结果前崩溃。重启时绑定真实且 Desired 匹配，第 426 行仍会把外部条目恢复为本方成功操作。

第 285、428 行又把“Delete 超时后仍看到条目”解释为“删除未生效，保持重试”。读回只能证明当前存在：删除可能已经完成，随后第三方重建了相同属性的条目；也可能原请求仍在执行。两者都不能直接归类为确定失败并再次删除。旧 Owned 记录不能自动证明当前条目身份连续。

**修改要求：**

- 删除第 426 行的弱证据恢复分支，所有入口采用同一归属准入表。Intent + Binding + Desired 不构成成功创建证据。
- 明确区分“目标状态满足”“操作结果已知”“当前资源归属可证明”；通用调用成功也不能不区分 Created、AlreadyExists 或幂等成功就认领。
- Delete 未知结果必须先判断旧执行者是否已终结、当前对象是否仍符合归属与操作前置条件；只有重新获得安全删除授权才可重试。不确定则保留 Pending/OutcomeUnknown/Uncertain。
- 共享表的协作假设不能只写“外部不高频修改”：单次并发修改也可能落在读回与写入之间。须承认无原子条件操作/独有身份时的保证边界，不宣称低频即安全。

**验收反例：** Add 遇外部抢先创建后崩溃；Delete 成功但响应丢失后外部重建；旧 Delete 尚未结束时读回；有日志但不能证明对象连续性的恢复。

## T2 — P1：修订删除了 Write-Ahead 与持久化失败边界

**位置：** 第 36、439–440 行；对比上一版第 8.2 节。

上一版明确规定 Intent 持久化后才执行系统操作，以及日志失败后停止新修改。本版删除了整个契约，仅留下架构图中的 WAL 名称和“拒绝新的破坏性修改”。WAL 这个名称不能代替执行顺序；“破坏性修改”也无法确定是否包含 Add。

**反例：** 日志不可写时，执行器把 Add 当作非破坏操作继续安装专用表路由或规则，然后崩溃；恢复端没有意图记录，不能证明归属或承担清理责任。图上存在 Journal 无法避免这一结果。

**修改要求：** 恢复最小持久化契约：需要恢复责任的系统修改，必须在对应 Intent 持久化成功后下发；分别保存实际结果与归属证据；结果落盘失败也不得丢失未决责任。持久化不可用时，普通增删改全部停止，既有在途副作用进入降级核对。确需紧急操作须单独定义授权与责任，不能用“非破坏性”隐式豁免。

具体日志格式、fsync 策略和检查点实现留到后续步骤，但执行前后顺序与失败边界属于当前行为契约。不要直接恢复上一版“读回存在即可 Commit 为自有”的问题，须与 T1 一起修正。

**验收反例：** Intent 持久化失败时系统调用数为零；系统成功但 Commit 写入失败；重启时存在未完成 Intent。

## T3 — P1：Linux 新槽位键把出口接口当成独立冲突边界

**位置：** 第 218–227 行。

第 220 行把 `oif` 加入 Linux 唯一槽位键。对当前使用的 IPv4 `NLM_F_CREATE | NLM_F_EXCL` 新增方式，改变出口接口并不能绕过同 table、prefix、DSCP/TOS、priority 的 EEXIST 冲突。仓库调用见 `easytier/src/common/ifcfg/netlink.rs:349–360`；[Linux v6.12 的 fib_table_insert](https://github.com/torvalds/linux/blob/v6.12/net/ipv4/fib_trie.c#L1176-L1227) 在对应 alias 上先检查 EXCL，并可在 Replace 分支替换该 alias 的转发信息，不能把 oif 当作旧对象的原子匹配保护。

**影响：** 规划器或资源锁若按这个 Key 分区，会把可能互相冲突、替换的操作看作两个独立对象。需求等价性已经区分出口接口，不需要通过修改平台冲突键来解决共享问题。

第 227 行反过来把“同域、同前缀、不同接口”一概定为不可调和，也过宽：不同表且具有明确、不重叠选流策略的需求可以共存。不等价不等于一定无法共存。

**修改要求：** 不冻结未经验证的全平台唯一键公式。后端按地址族、操作及支持的路由类型定义定位/冲突/修改范围；规范化属性用于判断等价性，不能自动用于缩小内核操作范围。区分“不可共享”“内核操作冲突”“同一流量的选路冲突”。

**验收反例：** IPv4 相同前缀/表/metric、不同 oif 的 EXCL 新增；改变 oif 的 Replace；不同表且选择条件互斥的同前缀需求。IPv6 单独验证，不能直接套用 IPv4 结论。

## T4 — P1：停止协议仍未覆盖需求撤销、清理失败和崩溃交接

**位置：** 第 236–241、376–404 行。

当前流程有三处不能据此安全实现的缺口：

1. **停止摄取不等于撤销 Desired。** 第 388 行只是拒收更新，第 393 行就遍历 Owned 删除，却要求遵守“当前无需求”的删除守卫。正常运行时的 Desired 仍在，删除全部被禁止；若绕过守卫，又可能删掉共享域中其他实例仍需的资源。须先定义实例停止与域停止的边界，通过同一协调器撤销相应来源并重新规划。
2. **清理阶段本身也会超时或失败。** 图中的成功分支只处理旧 Pending 排空，随后假定所有 Delete 都 ACK 成功。还可能出现删除被拒、返回未知、读回不匹配、守卫因归属不明拒绝清理。完成报告、遗留责任、截止时间和租约释放条件必须覆盖这些分支；逆序遍历集合也不等于满足路由/规则依赖顺序。
3. **进程崩溃后无法继续持有进程内协调器和文件租约。** 若委托宿主仍可能应用旧请求，新进程取得文件锁不等于旧写入权已被撤销。当前文字只解决协调器存活时的超时。需有宿主执行端实际检查的会话/epoch，或等效的终止旧会话、确认排空再接管协议；只丢弃旧回调不足以阻止旧配置生效。

**修改要求：** 给出停止状态转换与可交接条件：撤销作用域需求 → 停止旧计划 → 排空/隔离执行 → 按依赖清理或登记未完成责任 → 判定是否可交接。调用方等待期限与执行者存活期分离。对没有独占表租约的共享表模式也必须成立，不能把 FileLock 当作所有后端都有的安全机制。

**验收反例：** A 停止而 B 仍需要共享资源；域关闭时 Desired 非空；旧 Pending 排空后清理 Delete 超时；权限拒绝删除；进程崩溃后委托宿主迟到应用旧配置。

## T5 — P1：改为“后续增量更新”却仍允许跳过 revision，丢失与乱序后无法重建事实

**位置：** 第 357–358、441–442 行；对比上一版第 8.1 节及总纲第 3.1 节。

上一版明确要求每次来源更新都是完整快照，本次删掉了这条要求，改成订阅时获得全量、随后增量更新。同时第 442 行仍要求丢弃低 revision。两种规则组合后不正确。

**反例：** rev=10 增量加入 A，rev=11 增量加入 B；11 先到，10 随后被丢弃，最终需求只有 B。rev=10 通知丢失同样有问题。原子订阅仅解决首次窗口，不能补齐运行中的缺口。

**修改要求：** 恢复总纲的完整快照事实源：每次提交完整来源状态，通知可以合并或丢失，接收方可重新读取最新快照，观察连接重建/lagged 后必须重同步。若“增量”只是指更新通知，须明确它不承载唯一事实。若确实要引入状态 delta，则另需连续 revision/base revision 校验与缺口回退全量协议，不建议在此无意扩大协议复杂度。

**验收反例：** 更新乱序、漏通知、通知队列溢出、观察任务重启后，无需下一次业务变化即可恢复最新完整需求。

## T6 — P2：同一等待令牌遇冲突时有两个互斥的返回定义

**位置：** 第 359–362、410–417 行。

第 362 行把直接影响需求的冲突归为 Superseded；第 413 行却限定 Superseded 为来源版本被替代，第 414 行另外定义 Conflicted。来源没有发布新版本时发生冲突，调用者究竟得到哪个结果不确定；错误返回 Superseded 会让调用者误以为有新提交接替处理。

`DomainAggregate(u64)` 也尚未定义它捕获哪些来源版本，以及部分 HostConfirmed、部分 Verified 或失败如何汇总。仅给类型名并没有冻结聚合完成语义。

**修改要求：** Superseded 只表示被新提交替代；冲突保持独立可查询。定义聚合 token 的捕获范围、替代条件与完成级别汇总；若第二步暂不提供聚合等待，可明确仅冻结 Source token，将聚合 API 留待详细设计，避免现在暴露未定义接口。

## T7 — P2：平台验证声明仍缺乏与结论对应的证据

**位置：** 第 332–333 行。

本版新增“Windows 基础增删已有主线测试”“现有 CI 覆盖 macOS 基本连通”，但没有给出测试名或运行记录。仓库 `.github/workflows/core.yml:197–221` 的 Windows/macOS matrix 是构建；`.github/workflows/test.yml:109–141` 的测试构建与执行使用 Ubuntu。这些配置不能支持上述平台行为结论。

**修改要求：** 若有外部测试，附具体环境、基线和结果；否则写“静态核对，平台行为待验证”。此处不要求第一步提前执行第四步的全部平台测试，只要求证据状态准确。macOS/FreeBSD 的 CLI 首期选择可以进一步评估，但不能仅用“稳定”一词代替确认精度和局限；后续详细方案需落实当前承诺。
