# HostRouteManager 第二步方案：第十二轮复审

审查基线：`4cafe6da`；[`host-route-manager-step2-plan.md`](host-route-manager-step2-plan.md) Git blob 为 `576ef1f4099814372d3300207739a9a261a1a795`。本文行号对应此版本。

**结论：上一轮的未决 ADD 遗漏及无结果默认成功已修正；仍需修复解绑缓存的适用范围，以及回退查询绕过 deadline 的问题。** 主体架构无需变化，不要求增加版本、历史或通用任务框架。

## R1 / P1：上一次解绑结果会被当成本次结果

**位置：第 293–294、311–313、365–385、462–464、517–518、690–692 行。**

新增的 last_unbind_result 与共享 unbind_result 只在解绑完成后写入。新设备绑定以及开始新一轮解绑时，没有使旧结果失效。Handle 又会在发送失败或 ACK 关闭时直接使用共享缓存，因此存在以下顺序：

1. 设备 A 解绑成功，缓存为 `Some(Ok(()))`。
2. 绑定设备 B，缓存仍是 A 的成功。
3. B 解绑尚未完成，调用方超时后查询，得到的仍是成功；若 Manager 此时异常退出、ACK 关闭，unbind 的回退分支也直接返回 A 的成功。

这会重新引入“本次清理未确认却向 Host 报成功”的问题。即使旧结果是错误，也可能把 A 的错误错归给 B。全局 stop 只有一次终态，而 unbind 会随设备反复发生，两者不能直接套用同一种永久结果缓存语义。

**最小修正：** 把缓存限定在当前设备绑定及其解绑过程内。新绑定开始时使旧结果失效，新解绑进行中不能暴露上一设备的终态；只有确认属于本次操作的结果才可作为成功证据。Host 的生命周期调用应保持串行，不能让旧解绑的重试跨过新绑定再作用于新设备。

可以只保留一份当前绑定范围内的结果，并在既有 Host/Manager 接线中明确失效顺序，不必维护两份镜像缓存。若异常分支无法证明缓存属于本次解绑，直接返回 CleanupIncomplete，不能猜成功；无需为此建立全局版本或提交令牌系统。

**验证：** A 成功解绑后绑定 B，让 B 的删除暂停；查询不得返回 A 的成功。随后分别让 B 正常完成、ACK 关闭，结果必须属于 B。同一设备未完成解绑的重复调用仍应保持上一轮要求的结果一致性。

## R2 / P2：deadline 到达后仍会无期限等待结果锁

**位置：第 367、384、415–418、429、445、463–469 行。**

发送和 ACK 等待已经受 timeout_at 保护，但回退分支直接 await `query_cleanup_result()` / `query_unbind_result()`，这些方法内部使用异步 Mutex::lock。尤其第 415–418 行已经收到入队超时，deadline 已到，却又开始不受限制地等待清理结果锁。

结果锁被其他查询或结果发布者占用时，调用仍可能超过约定的 deadline。上一轮要求的“回退查询也不能脱离 deadline”尚未落实；把发送和 ACK 分别限时并不足以保证整个方法限时。

**最小修正：** deadline 已过时直接返回未完成，或仅做不等待的 try_lock 查询；尚有时间时，回退等待仍使用同一个绝对 deadline。独立的公开查询 API 可以继续异步等待，但 stop/unbind 内的限时路径不能无界调用它。不需要更换整套同步机制。

**验证：** 暂时持有结果锁，并制造命令入队超时或通道关闭，确认 stop/unbind 仍在 deadline 内返回，后台任务继续执行。

## 已关闭项与范围

- Stop 无结果时不再默认返回成功；取消分支已明确进入相同的清理与结果发布路径。
- 局部解绑已独立筛选旧设备的 unknown，覆盖未进入 installed 的未决 ADD。
- 同一设备重复解绑时，已保留并返回先前的未完成结果。
- 前几轮确定的 fd 保活、转发任务 join、局部解绑保留 backend 和其他接口路由等设计保持不变。
